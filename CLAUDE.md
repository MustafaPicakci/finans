# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Kişisel finans paneli: nakit hesapları, düzenli gelir/gider, kredi taksitleri, kredi kartı ekstreleri, nakit akışı takvimi ve canlı fiyatlı çok varlıklı portföy. **Auth: Faz 5.1** (kendi scrypt+session auth'umuz — [auth.ts](apps/server/auth.ts); tüm `/api` guard arkasında). **Kayıt herkese açık + e-posta doğrulaması zorunlu** (Faz 10 onboarding): **ilk kullanıcı = owner** (otomatik doğrulanır + sahipsiz veriyi devralır + otomatik giriş); **sonraki kullanıcılar** `email_verified=false` oluşturulur, aktivasyon e-postası gider, doğrulanana dek giriş 403 döner (`POST /auth/resend-verify` ile tekrar gönderilebilir). **Çok-kiracılık: Faz 5.2** — tenant tabloları `user_id` ile scope'lu (`prices/price_history` global piyasa verisi; `settings` global fx/tefas vs kullanıcı `user_settings`). **Prod ön koşulu**: çok-kullanıcı için çalışan bir e-posta yolu (+ `APP_URL`) şart — yoksa yeni kullanıcı aktive olamaz. **Faz 28**: gönderim yolu **açıkça** seçilir — `MAIL_PROVIDER` = `smtp` (varsayılan) | `gmail` | `resend`; örtük seçim (Faz 25'teki "anahtar doluysa o yola geç") bilerek kaldırıldı, çünkü hangi yolun aktif olduğu env'e bakınca görünmezse hata yanlış yolda aranır. HTTP yolları bir tercih değil zorunluluktu: **Render ücretsiz web servisleri giden SMTP portlarını (25/465/587) engelliyor** (port 25 tüm planlarda), log'da "connection timeout" olarak görünür ve ayar hatası sanılır — parola/host değiştirmek çözmez. `verifyMailConfig()` bağlantı hatalarında bu ipucunu açıkça loglar; seçilen yolun env'i eksikse hangi değişkenin eksik olduğunu söyler. **`gmail`** (Gmail API, 443): posta Google'ın kendi MTA'sından çıkar → DKIM/SPF hizalı, **domain gerektirmeden herkese ulaşır**; yetki `gmail.send` ile sınırlı (posta kutusunu okuyamaz — uygulama parolasından dar). Refresh token'dan 1 saatlik erişim jetonu üretilip önbelleklenir; açılışta gerçekten bozdurularak doğrulanır, `invalid_grant` hatası **"OAuth ekranı Testing'de kalmış"** ipucunu basar (Google o modda jetonu 7 günde bir iptal eder ve gönderim sessizce durur). Türkçe başlıklar RFC 2047 ile kodlanır. Token üreteci: [scripts/gmail-token.mjs](apps/server/scripts/gmail-token.mjs). **`resend`**: domain doğrulanmamışsa test göndereni kullanılır — **yalnız Resend hesabının kendi adresine** ulaşır (şifre sıfırlama yeter, başkasını aktive etmeye yetmez, yani çok-kullanıcılı akışı sessizce bozar); domain gelince tek değişen `MAIL_FROM`. **Yasal sayfalar (Faz 28)**: `/gizlilik` + `/kosullar` — [apps/web/public/](apps/web/public/) altında statik, **guard dışında** (giriş yapmadan okunabilmeli; Google OAuth doğrulaması anonim çeker), temiz URL için index.ts'te açık rota (yoksa SPA catch-all'una düşerdi) + `navigateFallbackDenylist` (yoksa service worker index.html döndürürdü). Faz 19: [mail.ts](apps/server/mail.ts) multipart düz metin + HTML gönderir (yalnız-HTML spam sinyalidir), açılışta `verifyMailConfig()` ile SMTP doğrulanır, `mailFromWarning()` Resend'in `From: Finans <resend>` tuzağını ve Gmail SMTP kullanımını uyarır, transport zaman aşımlıdır (yoksa yanıtsız sunucuda gönderim sonsuza dek asılı kalır — hata bile loglanmaz), gönderim hatası `lastMailError`'a yazılıp loglanır ama kayıt akışını **bloklamaz**. UI dili Türkçe; kod içi yorumlar ve enum değerleri de Türkçe (`'ALIŞ'`, `'SATIŞ'`).

pnpm workspace monorepo'dur: `apps/server` (Hono API + PostgreSQL), `apps/web` (React/Vite SPA), `packages/engine` (saf finans matematiği, ikisinin de bağımlı olduğu). Bu yapı bilinçli bir evrimin ilk adımı — hedef roadmap için [docs/PLAN.md](docs/PLAN.md)'a bakın (ledger veri modeli, mobil PWA, dosya importu, auth).

## Komutlar

```bash
pnpm install
pnpm dev            # concurrently: API (tsx watch, :8787) + Vite (:5173, /api proxy'li)
pnpm build          # pnpm -r build — her paket kendi build'ini çalıştırır (web: vite build + tsc; server/engine: tsc --noEmit)
pnpm test           # packages/engine vitest testleri (finans matematiği)
pnpm start          # prod: tek süreç, apps/server apps/web/dist statiklerini de sunar (:8787)
```

Tek bir paketi hedeflemek için `pnpm --filter @finans/server dev`, `pnpm --filter @finans/web build`, `pnpm --filter @finans/engine test` gibi filtreler kullanılır. `pnpm build` CI kapısıdır — her paket temiz geçmeli.

Node.js 22+ gerekir. **Veri tabanı PostgreSQL** (Faz 5.0'da `node:sqlite`'tan geçildi) — bağlantı `DATABASE_URL` env değişkeninden (bkz. `apps/server/.env.example`; yerel geliştirme için Docker Postgres önerilir). `apps/web`'de linter yok; vitest iki pakette çalışır — `packages/engine` (finans matematiği) ve `apps/server` (yalnız **AI ajan katmanı**: sahte sağlayıcı + enjekte edilen bağımlılıklarla, veri tabanına dokunmadan; `test-setup.ts` yalnız db.ts'in import-anı `DATABASE_URL` kontrolünü susturur). `pnpm test` = `pnpm -r test`, ikisini birden koşar. `apps/web`'de test yok. Eski SQLite verisini taşımak için: `pnpm --filter @finans/server migrate` (bir kez; `data/finans.db` → Postgres, id'ler korunur).

Docker: `docker compose up -d --build`. Compose iki servis çalıştırır: `db` (PostgreSQL, veri `./data/pg` volume'ünde) + `finans` (uygulama, `db`'ye `DATABASE_URL` ile bağlanır, healthcheck ile bekler).

## Mimari

pnpm workspace: backend = `apps/server` (Hono + PostgreSQL), frontend = `apps/web` (React/Vite SPA), paylaşılan finans matematiği = `packages/engine` (saf TS, React'e ve Hono'ya bağımlı değil). `apps/web` bu paketi `@finans/engine` olarak import eder (TS kaynağı doğrudan derlenir, ayrı build adımı gerekmez); `apps/server` da Faz 8.2'den beri tüketir (kart ekstre tutarı sunucuda `txShares` ile hesaplanır — istemciden gelen tutara güvenilmez).

### Para birimi (çok para birimi: TRY + USD)
TRY **taban (reconciliation) para birimidir**; hesaplar/gelir-gider/kart/kredi hep TRY. Yalnızca **portföy işlemleri (`trades`)** bir `currency` (TRY/USD) taşır — kripto/ABD hisse/ETF USD girilebilir. `prices`/`price_history` de sembolün doğal birimini saklar. Pozisyonlar **native** hesaplanır (`positions()` → `Position.currency`; avg/value/K/Z hep o birimde); net varlığa toplanırken `portfolioValueTry(pos, rates)` ile TRY'ye çevrilir (`rates = { usdTry }`, kaynağı `settings.fx_usd_try`). Üstteki **₺/$ görüntü seçici** (App.tsx, localStorage `finans-ccy`) net varlık özeti + KPI'ları nihai TRY rakamından çevirir (`convert(x,"TRY",ccy,rates)`); Nakit Akışı/Kayıtlar/Portföy satırları kendi biriminde kalır (portföy satırları native, projeksiyon TRY). Biçimleyici: `fmtMoney(v, ccy, dec?)` ([theme.ts](apps/web/src/theme.ts)). Yeni para birimi eklemek: `Currency` union + `convert`/`fmtMoney` + FX kuru kaynağı. **Yüzdeler için `fmtPct(x, dec?, zatenYuzde?)`** (aynı dosya): işaret **`%`'in ÖNÜNE** yazılır. Çağrı yerleri bunu elle kuruyordu (`{v>0?"+":""}%{(x*100).toFixed(1)}`) ve negatifte `toFixed` kendi eksisini getirip **"%-12,5"** çıkıyordu — Türkçede yanlış, üstelik pozitifte "+%6,8" yazıp negatifte biçim değiştirmek iki rakamı kıyaslanamaz kılıyordu. Yeni yüzde gösteren her yer bu fonksiyonu çağırsın.

### `packages/engine` — saf finans matematiği + tipler
Asıl karmaşıklık burada; React'ten/Hono'dan bağımsız, 181 vitest testiyle korunuyor (`pnpm --filter @finans/engine test`). Yeni bir hesaplama kuralı eklerken önce burada test yaz.
- [types.ts](packages/engine/src/types.ts) — domain tipleri (`AllData`, `Recurring`, `Trade`, ...); `apps/web/src/api.ts` bunları re-export eder.
- [date.ts](packages/engine/src/date.ts) — `hits` (ödeme günü kısa aylarda ay sonuna kayar), `ymOf`/`normYm` (ay biçimi ayrıştırma/doğrulama).
- [projection.ts](packages/engine/src/projection.ts) — `project(data, months)` → günlük `Day[]` nakit projeksiyonu. Hesap bakiyeleri bugünden başlar; recurring/loan/oneoff/kart-ekstresi hareketleri ilgili günlere işlenir. `Day.cashFunds` = o gün elde tutulan **para piyasası fonlarının** TRY değeri (`assets`'in alt kümesi); nakit sayılan fon sembolleri `settings.cash_funds`'tan (virgülle ayrık) okunur. Takvim gün rengini **etkin nakit = `bal + cashFunds`** ile belirler; fonlar Portföy sekmesindeki "nakit say" ile opt-in işaretlenir. Pür-nakit semantiği takvim dışında (Özet en düşük gün, Nakit Liste) korunur. **Faz 33 — borç ve net varlık**: `Day.total` (nakit+portföy+vadeli, borç DÜŞÜLMEMİŞ), `Day.debt` (o gün hâlâ duran ödenmemiş ekstre + kredilerin kalan taksit tutarı) ve `Day.worth` (`total − debt`). `worth` App.tsx'teki hero rakamıyla **tanım olarak aynıdır** — Özet'teki "Toplam Varlık" grafiği ile hero'nun aynı soruya iki cevap vermemesi için tanım tek yerde durur. Borç, ödeme nakitten çıktığı GÜN düşer (yoksa ödenen ekstre hem bakiyeden hem borçtan iki kez sayılırdı); testli değişmez: **ekstre/taksit ödemek net varlığı değiştirmez** (nakit azalır, borç da azalır). **Faz 35 — `netWorthBreakdown(data, rates)`**: net varlığın BİLEŞENLERİ (nakit/portföy/vadeli/kart borcu/kredi borcu). Tek sayı `Day.worth`'te vardı, kırılım ise App.tsx'in içindeki dört `useMemo`'da — yani ekran dışından (asistan) sorulamıyordu. Çapa **bugünün gerçek bakiyesidir** (`Σ accounts.balance`), `project(...)[0].bal` DEĞİL: gün 0 bugüne düşen PLANLI hareketleri zaten işlemiştir, oysa "ne kadar nakdim var" sorusunun cevabı bankanın şu an söylediği rakamdır — ikisi çoğu gün eşit, bugüne bir hareket düştüğünde ayrışır ve **ayrışmanın yönü testte yazılı** (kimse yanlış olanı "düzeltmesin"). Kart ve kredi borcu ayrı ayrı hesaplanır, biri diğerinden ÇIKARILARAK bulunmaz: çıkarma olsaydı projeksiyona üçüncü bir borç türü eklendiği gün o tutar sessizce "kart borcu" etiketiyle görünürdü — şimdi `kartBorcu + krediBorcu === Day.debt` testi patlar.
- [cards.ts](packages/engine/src/cards.ts) — `cardInfos`/`txShares`/`firstCutoff`/`dueOf`: kredi kartı ekstre matematiği. Harcama kesim gününe göre doğru ekstreye düşer, taksitler ardışık ekstrelere bölünür, geçmiş vadeli ekstreler ödenmiş sayılır.
- [loans.ts](packages/engine/src/loans.ts) — `loanRemaining`/`loanActiveOn`: kredinin kalan taksidi tarihten hesaplanır (elle güncelleme yok).
- [funds.ts](packages/engine/src/funds.ts) — Faz 17 "ödeme öncesi fon boz" önerisi: `cashFundSymbols`/`cashFundHoldings` (nakit sayılan fonlardan elde tutulanlar, TRY değerine göre sıralı), `cashGap(days, withinDays)` (**saf nakit** `bal` penceresinin **en derin** noktası — etkin nakde bakılsa öneri hiç çıkmazdı, ilk eksi güne göre bozulsa iki gün sonra yine açık verirdi), `fundSellSuggestion` (hangi fondan ne kadar, en geç ne zaman; fon yetmiyorsa tutar fonla sınırlanır + `covered:false`).
- [portfolio.ts](packages/engine/src/portfolio.ts) — **Faz 21: `trades` artık salt alım-satım değil, pozisyon OLAYLARI defteri** (`TradeSide = ALIŞ|SATIŞ|TEMETTÜ|BEDELSİZ`). `qtyDelta(t)` (adet etkisi: TEMETTÜ **0**, BEDELSİZ **+**) ve `cashDelta(t)` (nakit etkisi; BEDELSİZ 0) **tek kaynaktır** — adet toplama eskiden dört yerde (`positions`/`projection`/`funds`/`recall`) `side==="ALIŞ" ? +qty : -qty` diye tekrarlanıyordu, yani yeni bir tür eklendiğinde temettü sessizce SATIŞ sayılıp pozisyonu eksiltirdi. **TEMETTÜ**: adet ve maliyet değişmez, tutar `realized`'a yazılır (maliyetten düşmek satışta K/Z'yi iki kez saydırırdı). **BEDELSİZ**: adet artar, toplam maliyet sabit → ortalama maliyet kendiliğinden düşer, `price` her zaman 0. Sunucudaki `tradeBalanceDelta` da `cashDelta`'yı çağırır (ikinci kopya, yeni tür eklendiğinde ayrışırdı). `summarizeTrades` ayrıca `dividend` verir (realized'ın içinde, ayrıca raporlanır). `qtyFromAmount`/`amountFromQty` (Faz 17 tutar↔adet: tutar = **hesaba giren/çıkan para**, yani `tradeBalanceDelta`'nın tersi — `ALIŞ (tutar−fee)/price`, `SATIŞ (tutar+fee)/price`; TradeForm'un "Tutar gir" modu bunu kullanır, kaydedilen hâlâ adettir), `groupTradesByPortfolio(trades)` → `Map<portfolio_id|null, Trade[]>` (Faz 11 portföy grupları; pozisyonlar **grup başına ayrı** hesaplanır — aynı sembol iki portföyde ayrı ortalama maliyettir, tek listede değerlenince birleşir, net varlık değişmez), `portfolioGroupValueTry`; **K/Z yüzdesi**: `Position.unrealPct` + `pnlPct(pnl, cost)` (maliyet 0/negatifse `null` — 0'a bölme tek yerde çözülür). Toplam/grup oranı **yüzde ortalaması değildir**, toplam K/Z ÷ toplam maliyettir; `tradeLedger(trades)` → `TradeEntry[]` (Faz 12 hareket geçmişi: her işlemin öncesi/sonrası adet + ort. maliyet, satışta gerçekleşen K/Z, pozisyon kapandı işareti — `positions()` ile aynı matematik, ara adımları verir) + `summarizeTrades`; `positions(trades, prices)` → ağırlıklı ortalama maliyetli portföy (her pozisyon kendi `currency`'sinde); pozisyon kapanıp yeniden açılınca maliyet sıfırlanır. `convert(amount, from, to, rates)` (TRY↔USD), `portfolioValueTry(pos, rates)` (net varlık/alokasyon için TRY toplama), `portfolioValueHistory(trades, priceHistory, rates)` (USD-doğal geçmiş fiyatları güncel FX ile TRY'ye çevirir); Faz 13 grafik aralıkları: `sliceValueHistory(points, "1H"|"1A"|"3A"|"6A"|"1Y"|"TÜM")` + `bucketValueHistory` (uzun pencerede kova başına SON nokta = kapanış, ilk/son korunur) + `historyChange` (dönem değişimi mutlak+%). **Çözünürlük gündür** — `price_history` günde bir anlık görüntü tutar, aralık düğmeleri pencereyi daraltır, veriyi sıklaştırmaz.
- **Faz 27 — grafiğin iki modu**: `portfolioValueDecomposition` (değer + `contributed` + `gain` + `covered`) ve `twrSeries`/`rebasePct`/`symbolPriceSeries`/`symbolValueHistory`/`heldSymbols`/`coveredOnly`. Değer eğrisi tek başına "portföyüm arttı" der ama artışın ne kadarının KÂR, ne kadarının yeni para olduğunu söylemez; konan net para zaten `cashDelta`'nın tersidir (TEMETTÜ katkıyı AZALTIR → kâr sayılır, BEDELSİZ değiştirmez), böylece Δdeğer = Δkatkı + Δkâr tanımı gereği tam tutar. `walkValueHistory` tek yürüyüşte değer/katkı/kapsam üretir ve `portfolioValueHistory` onun ince sarmalayıcısıdır — iki kopya olsaydı biri yeni bir olay türünde sessizce ayrışırdı. **Kapsam kuralı**: fiyatı bilinmeyen AÇIK pozisyon o güne 0 katkı verir, yani seri portföyü küçük gösterir; TEFAS geriye doldurulamadığından bu sessiz eksiklik grafikte **sahte sıçramaya** dönüşürdü — `coveredOnly` o günleri eler, arayüz kaç gün düştüğünü yazar (karar PENCERE BAŞINA verilir: fiyat geçmişi olmayan bir sembol alınca katı kural son 1 ayı tamamen boşaltıp grafiği bozuk gösteriyordu). **% modunda portföy TWR'dir** (para giriş-çıkışı arındırılmış; basit değer oranı aynı veride %142 derken TWR %21 diyor — testli), **sembol/referans ise saf FİYAT getirisi** (pozisyon değerini yüzdeye çevirmek üstüne alım yapmayı "kazanç" gibi gösterirdi). TWR'nin kısıtı da testli: akış gününde fiyat anlık görüntüsü yoksa şişer.
- [holdings.ts](packages/engine/src/holdings.ts) — **Faz 31 pozisyon DÖNEMLERİ ve akış**: `positionPeriods(trades)` → `PositionPeriod[]`, `portfolioFlow(trades, rates)` → `FlowMonth[]`. `positions()` "şu an elimde ne var", `tradeLedger()` "tek tek ne oldu" der; aradaki soru — **bu varlık ne zaman girdi, ne zaman çıktı, sonuçta ne oldu** — cevapsızdı. Doğru birim sembol DEĞİL **pozisyon dönemidir**: Ocak'ta alınıp Mart'ta tamamen satılan ve Temmuz'da yeniden alınan THYAO iki ayrı iştir (ayrı giriş/çıkış tarihi, ayrı maliyet, ayrı sonuç) — motor zaten böyle davranıyordu (kapanışta ortalama maliyet sıfırlanır) ama bu hiçbir ekrana yansımıyordu. **Burada yeni matematik YOKTUR ve bu bilinçlidir**: ortalama maliyet + gerçekleşen K/Z mantığının zaten iki kopyası var (`positions`, `tradeLedger`), üçüncüsü yeni bir olay türünde sessizce ayrışırdı — bu dosya `tradeLedger()` çıktısının saf bir GRUPLAMASIDIR. Testte **ayrışma kapanı** var: sembol başına `Σ periods.realized === positions().realized` ve açık dönemin `qty`/`avg`'i `positions()` ile birebir. Kenar durumlar testli: adet sıfırken gelen TEMETTÜ (kapanış sonrası ödenen kâr payı) **yeni dönem açmaz ve kapanış tarihini değiştirmez**, son döneme yazılır; float artığı (`1e-12`) ve aşırı satış dönemi kapalı sayar (`EPS=1e-9`). `portfolioFlow`'un `netTry`'ı `walkValueHistory`'nin `contributed`'ı ile **aynı tanımdır** (`-cashDelta`, TRY'ye çevrili) — değer grafiğindeki "yatırdığın para" ile bu ekranın rakamı çelişmesin diye; ayrı bir tanım uydurmak aynı soruya iki cevap veren iki ekran demekti (testli).
- [corporate.ts](packages/engine/src/corporate.ts) — **Faz 36 kurumsal olaylar**: `kurumsalOneriler(trades, actions, opts)` (kullanıcının defterinde EKSİK olan bedelsiz/temettü) + `bedelliPlan` + `dripSet`/`dripAcikMi`/`dripToggle`. `BEDELSİZ`/`TEMETTÜ` Faz 21'den beri vardı ama elle giriliyordu; girilmezse adet eksik kalır, portföy kalıcı olarak düşük görünür ve fiyat yarıya indiği için düşüş **zarar gibi** okunur (ölçüldü: 30 likit BIST sembolünün 11'inde son 5 yılda bedelsiz var). **Yeni matematik YOKTUR** (holdings.ts'in gerekçesi): adet yürüyüşü `qtyDelta`'dan gelir, ortalama maliyete dokunulmaz — yapılan tek iş piyasa olayını defterle karşılaştırmak. Üç kural testli: **(1) "kaydettin mi?" penceresi `[bu olay, AYNI TÜRDEN bir sonraki olay)`** — düz "olaydan sonra BEDELSİZ var mı" ölçütü, iki kez bedelsiz veren hissede ikincisini kaydetmiş kullanıcıya birincisini de kaydetmiş gibi davranıp eksik kaydı gizlerdi; tür ayrımı da şart, yoksa kaydedilen bedelsiz temettü önerisini susturur. **(2) adet ex-date'ten ÖNCE ölçülür** (`t.date < a.date`) — ex-date'te alan hak kazanmaz. **(3) DRIP geri yatırım fiyatı ÖDEME GÜNÜNÜN fiyatıdır**, bugünkü değil (benchmarks.ts'in "o günün kuru" kuralı); fiyat yoksa tutar verilir, adet **uydurulmaz**. Temettü tutarı **BRÜTTÜR** — Yahoo brüt verir, hesaba stopaj düşülmüş net girer; bir stopaj oranı VARSAYILMAZ (oran değişir), arayüz "stopaj düşülmemiş" yazar ve form düzenlenebilir. **Öneri kayıt YAZMAZ**, önden dolu form açar: adet kullanıcının defteridir. **Kart düzeni (Faz 37'de elden geçti)**: olay başına TEK satır açıklama + sağa yaslı tek birincil eylem; "kaydetmezsen eksik kalır" ve "stopaj düşülmemiş" uyarıları her satırda tekrarlanmaz, kart dibinde BİR KEZ yazılır (brüt notu yalnız listede temettü varsa). Tarih `fmtD` ile biçimlenir (ham ISO değil), tür rozeti kendi rengini taşır (temettü yeşil = para girişi, bedelsiz mavi = adet değişimi) ve marka moru **yalnız** "Kaydet"te kalır — kart kenarlığı + başlık + iki düğme hep mor olunca hiçbiri öne çıkmıyordu (Faz 24 kural 2). Bilinmeyen/silinmiş kategori id'si kategorisiz sayılır (`katAdi` yalnız o kullanıcının kategorilerini taşır; ad uydurulmaz, başka kiracının adı sızmaz). ### Backend (`apps/server/`)
- [db.ts](apps/server/db.ts) — **PostgreSQL** (`pg` havuzu, `DATABASE_URL`). Şema `initDb()` içinde `CREATE TABLE IF NOT EXISTS` ile (server başlarken `await initDb()`). `node:sqlite` senkrondu; `pg` async olduğundan `db` yüzeyi de async: `db.all/get/run(sql, ...params)` ve atomik işler için `db.tx(async t => …)`. Eski `?` yer tutucuları db katmanında `$n`'e çevrilir; `INSERT ... RETURNING id` ile `run().id` (lastInsertRowid yerine). `datetime('now','localtime')`/`date('now','localtime')` yerine JS'te üretilen `nowLocal()`/`todayLocal()` parametreleri. `id` kolonları `GENERATED BY DEFAULT AS IDENTITY`, `REAL`→`double precision` (para hassasiyeti korunur). Yeni kolon eklerken `initDb()`'ye `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` deseniyle ekle. Taşıma script'i: [scripts/migrate-sqlite-to-pg.mjs](apps/server/scripts/migrate-sqlite-to-pg.mjs).
- [auth.ts](apps/server/auth.ts) — Faz 5.1 auth: `crypto.scrypt` ile parola hash/verify (sabit-zaman), server-side `sessions` (30 gün, revoke edilebilir). `index.ts`'te `/auth/*` rotaları guard'tan **önce** tanımlanır; `api.use("*")` guard'ı sonraki tüm `/api`'yi korur (401) ve `c.set("user", …)`. Kayıt herkese açık: **ilk kullanıcı** (`count===0`) owner olur (doğrulanmış + owner-bootstrap devri + otomatik giriş), **sonrakiler** doğrulanmamış oluşturulur + aktivasyon e-postası + `pending:true` (oturum açılmaz). E-posta token'ları (`verify`/`reset`) `email_tokens`'ta; `POST /auth/{verify,resend-verify,forgot,reset}`.
- [data.ts](apps/server/data.ts) — **Faz 35** `loadAllData(uid, {gecmis})`: kullanıcının `AllData`sını yükleyen TEK yer. `GET /api/all`ın gövdesiydi; asistanın okuma araçları da (net varlık, nakit projeksiyonu) aynı veriyi ister ve ikinci bir yükleyici **fiyat birleştirmesini** (global auto + kullanıcının elle override'ı, çakışmada kullanıcı kazanır) ve **ayar birleştirmesini** (global fx/tefas + `user_settings`, `cash_funds` buradan) kopyalardı — biri düzeltilmediği gün asistan ekrandan farklı bir portföy değeri söylerdi. `gecmis` bayrağı fiyat/referans geçmişini opsiyonel yapar (yalnız değer grafiği kullanır; asistan hiç bakmaz, yoksa her soru yüz binlerce satır çekerdi). Bu taşımada Faz 34'ten kalan bir kusur da düştü: `/api/all` içindeki `Promise.all`a `ai_conversations`/`ai_messages`/`ai_actions` sorguları eklenmiş ama **sonuçları hiç kullanılmıyordu** (22 değişken, 25 sorgu) — yorumu bile "KVKK indirmesine girmesi gerekir" diyor, yani satırlar `/api/export`a aitti ve orada zaten var; yani her sayfa açılışı ve her mutasyon sonrası `reload()`, monoton büyüyen `ai_messages` dahil üç tabloyu `SELECT *` ile boşuna çekiyordu.
- [index.ts](apps/server/index.ts) — Hono rotaları. Auth guard'ından sonra: tüm okuma **tek** `GET /api/all` ucundan (frontend her mutasyon sonrası hepsini yeniden çeker), kullanıcıya scope'lu (`WHERE user_id=?`; `settings` = global + `user_settings` merge). Yazma tarafı çoğunlukla `crud(route, table, cols)` fabrikasıyla üretilir — **Faz 5.2'de crud tek noktadan tenant-scope'lar** (POST `user_id` enjekte, PUT/DELETE `WHERE id=? AND user_id=?`), yani yeni tablo için CRUD eklemek yine tek `crud(...)` çağrısı ama otomatik izole. Yeni bir tenant tablosu eklerken `TENANT_TABLES`'a da ekle (db.ts — scoping + owner devri onu kullanır). **İstisna: `transactions`** jenerik crud yerine elle yazılmış POST/DELETE (+ toplu içe aktarma için `POST /transactions/bulk`: tek db.tx içinde N kayıt, hesap/kategori sahipliği önden doğrulanır, en fazla 500 satır) kullanır çünkü yan etkisi var — `account_id` verilmişse INSERT hesabın bakiyesini `amount` kadar oynatır (gider −, gelir +), DELETE geri alır; ikisi de `BEGIN/COMMIT` ile atomik, PUT yok (düzenleme = sil + yeniden ekle). Fiyat ve ayar uçları da elle yazılmıştır. Prod'da `serveStatic` ile `apps/web/dist` sunulur (yol `apps/server`'a göre relatif — server her zaman pnpm filter ile kendi dizininden çalıştırılmalı). `node-cron` her 15 dk `refreshAll()` çağırır. **Faz 23**: `GET /api/health` guard'tan **önce** tanımlıdır (herkese açık; yalnız süreç+DB canlılığı, DB'ye erişilemezse **503** → monitör "ayakta ama kullanılamaz"ı da görsün) ve prod'da `KEEPALIVE_URL`/`APP_URL` varsa cron 10 dk'da bir kendi genel adresini yoklar — Render ücretsiz katmanı 15 dk atıllıkta uyutuyor, soğuk başlangıç mobil "SMS paylaş" akışını bitiriyordu. Bu ping yalnız **uyanık tutar, uyandırmaz** (süreç uyursa cron'u da durur) — asıl güvence dış uptime monitörüdür, README'de kurulumu var. **Faz 5.4 + deploy-öncesi tur**: güvenlik başlıkları + **CSP** + prod'da **HSTS**; **genel API rate-limit** (IP 300/dk) + auth uçları (10/5dk) + e-posta başına login brute-force (5→429) + zamanlama-güvenli login; gövde sınırı 256KB (413); `app.onError` jenerik 500; yazma uçlarında güvenli JSON parse (bozuk→400); `/prices/refresh` 6/dk. KVKK: `GET /api/export` (veri indir) + `POST /api/account/delete` (parola onaylı, cascade). Yeni güvenlik davranışı eklerken bu desenleri (rate-limit helper'ı `rateLimited`, `loginFails`) izle.
- [prices.ts](apps/server/prices.ts) — Best-effort fiyat çekme. Her varlık türü (`BIST`/`FON`/`ALTIN`/`DOVIZ`/`KRIPTO`/`ETF`) için ayrı fonksiyon; bir kaynak formatını değiştirirse **sadece** ilgili fonksiyon güncellenir. `refreshAll()` yalnızca `trades` tablosunda tutulan sembolleri tazeler, `prices` tablosuna `source='auto'` ile upsert eder. **Para birimi**: fiyat sembolün *doğal* biriminde saklanır — KRIPTO/ETF işlemi USD birimliyse ham USD (`×usdTry` YAPILMAZ), TRY ise (eski) çevrilir; diğer türler TRY. USD/TRY kuru her tazelemede `settings.fx_usd_try`'ye yazılır (portföyde varlık olmasa bile, holding kontrolünden önce — görüntü çevrimi için). **Elle girilen fiyatlar KULLANICIYA ÖZEL** (Faz 5.2.1): `PUT /api/prices` global `prices`'a değil `user_prices (user_id, symbol, asset_type)` tablosuna yazar; global `prices` yalnız otomatik/piyasa fiyatı tutar. `GET /api/all` global auto + kullanıcının override'ını merge eder (override kazanır, `source='manual'`); "sıfırla" (`DELETE /api/prices/...`) kullanıcının override'ını siler → global auto'ya döner. Böylece bir kullanıcının eli başkasının değerlemesini etkilemez. `ETF` (VOO, QQQ... yurt dışı borsa) Yahoo'dan sorunsuz çekilir. **Faz 27 — geriye doldurma**: `yahooHistory(sym, range)` (aynı Yahoo ucu, farkı yalnız `range`) + `backfillPriceHistory()` `price_history`'yi 2 yıl geriye doldurur; fiyat geçmişi eskiden yalnız uygulama çalıştığı günden itibaren biriktiğinden "1Y" düğmesi anlamsızdı. **Kapsam dışı: FON** (TEFAS aracısı günde tek gün verir, 1 yıl ≈ 250 çağrı = kota) **ve ALTIN** (truncgil yalnız anlık) — bu yüzden backfill portföy TOPLAMINI uzatmaz, uzayan şey tek tek sembol serileri ve referans karşılaştırmasıdır. Uç: `POST /api/prices/backfill` (saatte 2, bakım işi; asistana kapalı) — ama **elle çağırmak gerekmez**: `autoBackfill()` ([benchmarks.ts](apps/server/benchmarks.ts)) açılışta (sunumu bloklamadan) ve günlük cron'da koşar. Referanslar için ölçüt tablo derinliği (<60 gün → 2 yıl, yoksa 5 gün), semboller için `settings.backfilled_symbols` listesi — tek bir "yapıldı" bayrağı yetmezdi, sonradan alınan bir hisse listeye girmez ve geçmişi sebebi görünmeden kısa kalırdı. **`FON` (TEFAS)**: resmi API bot-koruması arkasında olduğundan RapidAPI'deki resmi olmayan bir aracı (`RAPIDAPI_KEY` / opsiyonel `RAPIDAPI_KEY_2` env değişkenleri, `.env.example`'a bakın) kullanılır — tek fon sorgusu yok; `returns-by-date` ile bir günün TÜM fon türleri **tek istekte** çekilip **tamamı** saklanır (kota israf edilmesin diye sadece tutulanlar değil). NAV günde bir hesaplandığından `settings.tefas_last_fetch` ile günde bir kez çağrılır (ücretsiz kota sınırlı); birinci anahtar 429 alırsa otomatik ikinciye geçilir. Anahtar yoksa/kota dolarsa fonlar elle fiyatlanır (Portföy sekmesinde rozet+sıfırla).

#### Arayüz kuralları (Faz 24 — bunlara uymayan ekran tutarsız görünür)

Beşi de gerçek bir kusurdan doğdu; yeni ekran yazarken **varsayılan** kabul et:

1. **Mobil satır dilbilgisi.** Liste satırları `Row` (`.ui-row`) mobilde sarmalanır ve düzen `order` ile **sabittir** — içerikten bağımsız olarak `satır 1: [row-lead] [row-title…] [row-amount] [row-end]`, `satır 2+: kalan kontroller`. `Row` görünmez bir `row-break` öğesi basar, kontrolleri alt satıra o iter. Dört sınıfın anlamı: `row-lead` baştaki sabit öğe (tarih/ikon/renk noktası), `row-title` satırın kimliği, `row-amount` tutar, `row-end` küçük satır eylemleri (✎ ✕). **İşaretsiz içerik alt satıra düşer** — yeni satırda bu sınıfları vermeyi unutma. Kurallar `!important` taşır çünkü bileşenler stillerini inline verir. `Row` kullanmayan özel satırlarda (Hareketler, Plan) aynı sınıflar + elle `row-break` konur. Masaüstünde bu kurallar yok: tutarı orada da sağa yaslamak için `row-title`'a `flex:1`, tutara `marginLeft:auto` inline verilir.
2. **Filtre ≠ eylem.** Görünümü değiştiren her kontrol `FiltreSeridi` içine girer (çukur şerit, ▽ işareti); veri değiştiren düğmeler kartın yüzeyinde kalır. Marka moru "sıradaki eylem"e ayrılmıştır — seçili filtre beyaz yüzey + mor metindir, mor dolgu değil.
3. **Uzun yardım metni `Aciklama` arkasına.** Bir kez okunan açıklamalar ⓘ ile katlanır (tercih localStorage'da). **İstisna**: form alanı ipuçları ve açık panel içi görev metni katlanmaz — onlar yazarken okunur.
4. **Silme onay ister.** Çıplak `<button style={css.del}>` YAZMA; `SilDugmesi` kullan ve `sonuc` ile o kaydın **yan etkisini** yaz (virman iki bacak, hesap tüm defter, kategori işlemleri kategorisiz bırakır…). Görülmeden verilen onay, onay değildir.
5. **Modal portal şart.** `Modal` `createPortal` ile `document.body`'ye çıkar. Sebep: `.tab-grid`'in `animation: … both` dolgusu tarayıcıda kalıcı transform sayılır ve `position:fixed` için kapsayıcı blok yaratır — portal olmadan sekme içinden açılan modal ekranın binlerce piksel aşağısında ortalanır. **Sekme içeriğine `transform`/`animation` eklerken bunu hatırla.**

6. **Genişlik veren her yerde `boxSizing`.** Projede **global `* { box-sizing: border-box }` YOK** — `css.input` kendi içinde tanımlar, `css.card` etmiyordu. Kartlara normalde genişlik verilmez (blok öğe, `width:auto` → padding zaten içeride), ama `width:"100%"` verilen iki yerde (giriş ekranı kartı, `Modal`) padding 22×2 + kenarlık 1×2 genişliğe EKLENİYORDU: 390px telefonda 358px'lik yuvaya 404px'lik kart çiziliyor, giriş kartının sağ kenarı ekranın dışında kalıyor, modal iki yandan kırpılıyordu. `css.card` artık `border-box` (genişlik verilmeyen kartlar için etkisiz, yani hiçbir ekran kıpırdamaz). Aynı tuzak `min-height` + `padding` ikilisinde de var: giriş ekranının kabı `100dvh + 32px` oluyor ve içerik rahat sığsa bile sayfa her zaman 32px kayıyordu. **Yeni bir yere `width`/`height`/`min-height` yazarken padding'i olup olmadığına bak.**

Veri zaten `/api/all` ile geliyor; sayfalanan şey yalnız RENDER (asıl maliyet orada: her satır düğmeli/seçicili karmaşık bir DOM ağacı). `limit` + `slice` deseni `kayitlar` sekmesindekiyle aynıdır, etiket de aynı dili konuşur ("Daha eski hareketler (N)"). **Dönem özeti `shown` üzerinden hesaplanır, görünen dilim üzerinden DEĞİL** — sayfaya bağlasaydık "daha göster"e her basışta alış/satış toplamları büyür, hangi rakamın doğru olduğu belirsizleşirdi; kaç satırın gizlendiği de açıkça yazılır ("50 / 81 işlem gösteriliyor"), sessizce kesilen liste "işlemim kaybolmuş" dedirtir). **Pozisyon listesi `openPositions()` ile süzülür** — `positions()` işlem görmüş HER sembolü döndürür (kapananların `realized`'ı toplamlarda gerekli), süzülmediği için satılmış hisseler "0 adet"le listede duruyor ve grup başlığındaki "N varlık" sayacı onları sayıyordu; kapananlar detayda katlanır **"Kapanan pozisyonlar"** bölümünde giriş→çıkış tarihi + gerçekleşen K/Z ile durur. Toplamlardaki `gerç. K/Z` bilerek **süzülmemiş** `pos` üzerinden hesaplanır (listeyle birlikte süzmek geçmiş kârı sessizce silerdi).
  - **`nakit`** — **Faz 37'de PİYASA KATMANI eklendi.** Sekme önce bir nakit takvimidir ve öyle kalır: hücrenin söylediği şey bir RAKAMDIR (etkin nakit) ve gün rengi bakiyeden gelir. Piyasa tarihleri (bilanço / bedelsiz-temettü ex-date / TCMB-Fed-TÜİK) bunun ÜSTÜNE biner — hücrede tek küçük **kare** (planlı hareketin yuvarlak noktasından ayrılsın diye: aynı hücrede ikisi bulunabiliyor, aynı biçim olsalar sayılırlardı), ayrıntısı var olan gün panelinde ve liste görünümünde "piyasa" bölümü olarak. Üstteki tek anahtarla kapatılır (tercih `finans-nakit-piyasa`'da). **Faz 37 bunu önce AYRI BİR SEKME olarak kurdu ve yanlıştı**: iki ekranın ay şeridi, ızgarası, gün paneli ve liste görünümü aynı bileşenin iki kopyasıydı; gerçekten farklı olan tek şey hücrenin ne söylediğiydi (rakam mı, tür mü) ve aynı 47px'lik kutuda ikisi duramaz. Doğru cevap iki eşit ekran değil **birincil + katman**. Katmanın penceresi bu EKRANIN penceresidir (ayın başı → projeksiyon ufku), yani aylar öncesinin ex-date'i burada aranmaz — o soru Özet'teki "kaçırdığın kurumsal olay" kartınındır. `takvimOlaylari` **tür süzgeciyle** ve `days` BOŞ geçilerek çağrılır: planlı hareketler bu ekranda zaten `Day.ev`den geliyor, ikinci kez istemek aynı satırı iki kez çizerdi. Piyasa satırında alt yazı YALNIZ `detay` varsa çizilir — `etiket` ("Fed") başlığı ("Fed faiz kararı (FOMC)") tekrar ediyordu.
  - **`kayitlar`** — **Faz 26** — eski `rapor` sekmesinin yerine: TÜM hareket türlerinde arama. Rapor dört jenerik grafik parçasıydı ve kullanıcı hiç kullanmıyordu; iki sebebi vardı — harcamanın çoğu kartta olduğundan grafikler neredeyse boştu, ve ekran bir SORUYA cevap vermiyordu. Yeni ekran tek soruya cevap verir: "şu kaydı ne zaman girmiştim?". Grafik yoktur ve **ALTTAKİ LİSTE hâlâ toplam üretmez** — türler arası ham toplam yanıltıcı olurdu, çünkü kart harcaması ile onun ekstre ödemesi aynı parayı iki kez sayar ve virman hiç para hareketi değildir. Kategori yönetimi Tanımlar'a taşındı. **Faz 40 — üstte ayrı bir "Harcama Özeti" kartı var** ([Ozet.tsx](apps/web/src/features/kayitlar/Ozet.tsx)): `harcamaOzeti`'ni çağırır, yani tam da o tuzağı temel seçtirerek çözer ve hangisini kullandığını yazar (yasak duruyor, çözülen şey ayrı bir bölümde sunuluyor). **Dönem ve aramayı üstteki şeritle PAYLAŞIR** — ayrı bir tarih seçici, aynı ekranda birbirini tutmayan iki rakam demekti; kendi kontrolleri yalnız temel + kırılım. Tür süzgeci özete uygulanmaz ve bu sessiz bırakılmaz (kapsam dışı tür seçiliyse panel yazar). `uyari` satırları **katlanmaz**, aynen basılır (rakamın anlamını değiştirirler). Panel `finans-kayitlar-ozet` ile kapatılır (nakit sekmesinin piyasa katmanıyla aynı desen). Kırılım "aya göre" iken liste **ters çevrilir** (engine kronolojik döndürür ama dilim baştan alınır — yoksa "1 yıl"/"Tümü" en ESKİ 8 ayı gösterip içinde bulunulan ayı saklıyordu) ve `DahaFazla` yönü de ona göre seçilir. Kırılımda gideri olmayan kova gelirini yazar (yoksa maaş kategorisi "₺0,00" görünüyordu) ve ay etiketi `tr-TR` ile biçimlenir (engine "2026-09" döndürür — alttaki listenin ay başlığıyla çelişmesin). **Faz 41 — "Kategorile (N ad)" düğmesi** ([Kategorile.tsx](apps/web/src/features/kayitlar/Kategorile.tsx)): uyarı bir EYLEM istiyorsa eylemi de sunmalı; Faz 39/40 geçmiş veride yalnız "N TL kategorisiz" uyarısı üretiyordu ve tek düzeltme yolu kayıtları tek tek açmaktı. Birim kayıt değil **AD**: satırlar `normName` (recall.ts'in aynı anahtarı) ile gruplanır, seçim grubun TAMAMINA yazılır; sıralama tutara göre (en büyük parça en tepede). Aynı adla daha önce kategorilenmiş kayıt varsa seçici **önden dolu** gelir ama **hiçbir şey kendiliğinden yazılmaz** (Faz 36'nın "öneri kayıt yazmaz" kuralı). Gruplama anahtarı `yön + ad` (aynı ad hem gelir hem gider olabilir, kategori listesi türe göre süzülüyor); **ekstre ödemeleri listeye girmez** (harcama değil, kart borcunun kapanışı). **Liste kart harcamalarıyla sınırlı DEĞİL**: kategorisiz hesap işlemleri de girer (onlar da kırılımda "(kategorisiz)" kovasına düşer) — ama kullanıcı geri bildirdi ki panelin uyarısı karttan söz ederken listede "Maaş" görmek şaşırtıyor, çünkü **satır kaynağını yazmıyordu**. Çözüm satırı gizlemek değil: her satır artık kart/hesap adını yazıyor ve modalın içinde sayaçlı bir **kaynak süzgeci** var (Hepsi | Kart harcaması | Hesap işlemi). Uzun kapsam açıklaması `Aciklama` arkasına alındı (Faz 24 kural 3) — yedi satırlık paragraf listeyi 390px'te ekranın yarısına itiyordu. Sayaç ile modalın listesi **aynı fonksiyondan** gelir (`kategorisizGruplar`) — iki kopya olsaydı düğme "3 ad" deyip modal 5 satır açardı.
  - **`profil`** — **Hesabım** — KULLANICI hesabı: veri indirme + hesap silme. `profil` bilerek `NAV` dizisinde **değildir** (menü zaten sekiz sekme); kenar çubuğundaki kullanıcı kartından ve mobil ⋯ menüsünden açılır, başlığı `PROFIL_META`'dan gelir. Bu ayrım isim çakışması yüzünden yapıldı: `hesaplar` sekmesinde "hesap" = banka/nakit/aracı kurum, orada duran "Hesabı sil" düğmesi bir banka hesabını siliyormuş gibi okunuyordu.
  - **Ortak kural (tüm sekmeler):** Sekmelerde işlem girişi formu **ve işlem ekleme düğmesi** yoktur (yalnızca hesap/kategori/kart gibi *tanım* formları); işlem girişi global "+ Ekle"dendir — Faz 24'te bu kuralın iki istisnası (Portföy "+ İşlem", Kart "+ Harcama") kaldırıldı.
- [api.ts](apps/web/src/api.ts) — HTTP istemcisi; domain tipleri `@finans/engine`'den re-export eder.

### Veri modeli notları
- **Fiyat geçmişi tutulmaz.** `prices` her sembol için tek güncel satır (`PRIMARY KEY (symbol, asset_type)`). Takvimdeki geçmiş günlerin portföy değeri de bugünkü fiyatla değerlenir.
- **`statement_payments.tx_id` (Faz 40'ta `/api/all`'a açıldı)**: ekstre ödemesinin deftere yazdığı `transactions` satırı. Sunucu bunu Faz 8.2'den beri tutuyordu ama istemciye göndermiyordu; harcama özetinin tüketim temeli ekstre ödemesini **adından tanıyamaz** ("Akbank ekstresi" elle de yazılabilir) ve elemek zorundadır, yani alan olmadan arayüz doğru toplamı hesaplayamıyordu. Tip opsiyonel: eski sunucu/PWA önbelleği taşımaz → eleme yapılamaz ve panel bunu yazar, sessizce yanlış toplam vermez.
- **Kart harcamasının kategorisi (Faz 39)**: `card_txs.category_id` (nullable, `ON DELETE SET NULL` — `transactions.category_id` ile aynı kural: kategori silinmesi harcamayı silmez, kategorisiz bırakır). Mevcut satırlar NULL kalır ve **geriye dönük tahmin YAPILMAZ** (addan kategori türetmek, ekstre ödemesini adından tanıma hatasının aynısı olurdu). Uç tarafı tek satır: jenerik `crud("cardtxs", …)` kolon listesine eklendi — `crud` kategori SAHİPLİĞİNİ doğrulamaz (tıpkı `POST /transactions` gibi; toplu içe aktarma doğrular) ama yabancı id bir şey sızdırmaz: kullanıcının kendi kategori listesinde çözülmez, engine onu kategorisiz sayar. **Düzenli gider karta düşerken kalemin kategorisi taşınır** (`realizeOccurrence`) — öncesinde aynı kalem hesaba düşünce kategoriyi koruyor, karta düşünce sessizce kaybediyordu.
- **Kurumsal olaylar (Faz 36)**: `corporate_actions (symbol, asset_type, date, kind, value, currency)` — GLOBAL, tıpkı `price_history` gibi (bir şirketin bedelsizi herkes için aynıdır). `kind`: `'bolunme'` (value = adet çarpanı) | `'temettu'` (value = hisse başına brüt tutar). Kaynak: zaten çağırdığımız Yahoo `chart` ucu + `events=div,split` ([prices.ts](apps/server/prices.ts) `yahooEvents`/`refreshCorporateActions`) — yeni veri sözleşmesi yok. Oran `splitRatio` METNİNDEN değil ham `numerator`/`denominator`'dan okunur (Türkiye'de bedelsiz yuvarlak değildir). `/api/all`'a **`gecmis` kapısının arkasından ve kullanıcının sembolleriyle sınırlı** girer (`price_history` dersi + Faz 35'in kapısı): onu tek kullanan arayüzdeki "kaçırılan olay" kartı, asistanın okuma araçları için çekilmesi gereksiz. Tarama **günlük cron'da VE açılışta** koşar — yalnız cron'a bağlı kalsaydı deploy sonrası tablo bir güne kadar boş kalır ve uyarı hiç çıkmazdı (`autoBackfill`'in gerekçesinin aynısı). **Kapsam: yalnız BIST/ETF** (fonlar bölünmez, TEFAS NAV'a yansıtır). Yahoo BIST için **bilanço tarihi vermiyor** (`events=earn` boş döner) — şirket takvimi istenirse KAP gerekir.
- **DRIP (temettü geri yatırımı)**: `user_settings.drip_symbols` — virgülle ayrık `TYPE:SYM`, `cash_funds` deseninin aynısı (ayrı tablo açmaya değmeyecek kadar küçük bir opt-in). `cash_funds` düz sembol tutar, burada TÜR de var çünkü aynı sembol iki varlık türünde olabilir. İşaret İŞLEME değil **POZİSYONA** aittir — aynı hisseyi ikinci kez alınca hangi işlemin kazanacağı sorusu doğardı; bu yüzden anahtar hem alış formunda (karar orada verilir) hem pozisyon ayrıntısında aynı ayarı yazar ve **anında** kaydedilir (bir tercih, bir işlem değil).
- **Fiyat yaşı ve `AllData.now`**: `prices.updated_at`, fiyatın oluştuğu an DEĞİL bizim onu son kez başarıyla ÇEKTİĞİMİZ andır (Yahoo piyasa kapalıyken de son kapanışı döner, yani pazar günü çekilen bir BIST fiyatı "2 dk önce" görünür ama cuma kapanışıdır) — rozet bu yüzden "çekildi" der ve tooltip gecikmeyi (BIST ~15 dk, TEFAS günde bir NAV) açıkça yazar. Yaş `fiyatYasi(updated, now)` ([theme.ts](apps/web/src/theme.ts)) ile ölçülür ve **`now` `/api/all`'dan gelir, `Date.now()`'dan değil**: `nowLocal()` timezone taşımayan bir duvar saati damgasıdır, sunucu (Render) UTC'de kullanıcı UTC+3'te olduğundan tarayıcı saatiyle karşılaştırmak taze fiyatı sürekli "3 sa önce" gösterirdi; aynı saatten iki damganın FARKI zonedan bağımsızdır. `now` yoksa (eski sunucu/PWA önbelleği) yaş **gösterilmez**, tarayıcı saatinden uydurulmaz. Üst çubuktaki global rozet **en YENİ** otomatik damgayı alır (en eskisini değil): sorduğu soru "her fiyat taze mi" değil "tazeleme çalışıyor mu" — çekilemeyen tek bir sembol (fon kotası) en eski damgayı günlerce eski tutar ve sürekli yanlış alarm verirdi. Elle girilen fiyatlar global rozetin dışındadır (yaşları kullanıcının yazma anıdır, boru hattı hakkında bir şey söylemez) ama satır ayrıntısında "girildi" diye görünür. Mobilde yaş ⋯ menüsündeki "Fiyatları yenile"nin alt satırındadır — 390px üst çubukta yer yok, karta koymak Faz 32'de çıkarılan üçüncü kopyayı geri getirirdi.
- **Şirket takvimi (Faz 37)**: `company_events (symbol, asset_type, kind, date, tahmini)` — GLOBAL (`corporate_actions` gibi: bir şirketin bilanço günü herkes için aynıdır), sembol başına **TEK satır** (`PRIMARY KEY (symbol, asset_type, kind)`) çünkü takvimin işi olan yalnız SIRADAKİ tarih; geçmişte kalanlar her turda silinir (yoksa takvim geçmişte "yaklaşan bilanço" çizerdi). Kaynak Yahoo `quoteSummary/calendarEvents` — `chart?events=earn` BIST'te BOŞ döner (ölçüldü), bu uç ise **crumb** ister: çerez → `/v1/test/getcrumb` → `&crumb=`. Projedeki tek yeni kırılganlık bu, bilinçli kabul edildi (alternatif KAP'tı, POST sorgu ucu bot koruması arkasında ve Render'dan bağlantı hiç kurulmuyor); bozulursa yalnız bilanço satırları düşer, takvimin defter tarafı ve makro tarihler çalışır. **`tahmini` AKTARILIR, gizlenmez**: Yahoo `isEarningsDateEstimate` ile tarihin duyurulmuş mu yoksa geçen yıldan mı türetildiğini söylüyor (ölçüldü: THYAO/GARAN `false`, ASELS/BIMAS `true`) — arayüz `~` ile yazar. **İleriye dönük temettü/bedelsiz YOK** ve olmayacak: `exDividendDate` çoğu sembolde SON ex-date'i döndürüyor; yani aksiyoner olan tek olay alınamayan olay, arayüz bunu saklamak yerine "beklediğin temettüyü Plan'a tek seferlik gelir yaz" der. `/api/all`'a `gecmis` kapısının arkasından ve kullanıcının sembolleriyle sınırlı girer (`corporate_actions` deseni).
- **Referans endeksler (Faz 27)**: `benchmark_history (key, date, price)` — global, TL'ye çevrilmiş; kayıt [apps/server/benchmarks.ts](apps/server/benchmarks.ts) (`refreshBenchmarks`, cron'da günde bir 5 günlük pencereyle). `price_history`'ye YAZILMADI: `AssetType` kapalı bir birleşim ve TradeForm'un tür açılırını besliyor — oraya "ENDEKS" eklemek S&P 500'ü alınabilir bir varlık gibi gösterirdi. `/api/all`'da 2 yılla sınırlı gönderilir (5 seri × ~500 gün); kullanıcıya göre daraltılamaz çünkü karşılaştırmanın anlamı zaten "tutmadığın şeye göre nasılsın".
- **`price_history` global ama `/api/all` KULLANICININ sembolleriyle sınırlı gönderir** (EXISTS + trades). TEFAS tazelemesi bedavaya gelen tüm fonları (yüzlerce) her gün bu tabloya yazar — bu bilinçli (yeni fon eklenince fiyatı hazır olsun) ama filtresiz okuma her sayfa açılışında tüm piyasanın geçmişini indiriyordu (ölçüldü: 770 kB / 5,5 sn, her gün büyüyor). Veri tek yerde kullanılıyor: portföy değer grafiği. **Yeni bir global tabloyu `/api/all`'a eklerken aynı soruyu sor**: bu satırların hepsi bu kullanıcı için anlamlı mı? (`prices` bilinçli olarak filtresiz kalır — sembol başına tek satır, ve TradeForm hiç işlem yapılmamış bir sembolün fiyatını oradan doldurur.)
- **Düzenli gelir/gider (Faz 9)**: kimlik ile tutar ayrıdır. `recurring` = kalıcı kimlik (ad/gün/tür/hedef/auto + yaşam penceresi `from_month`/`to_month`, `'YYYY-MM'` dahil); tutar `recurring_amounts (recurring_id, from_month, amount)` zaman çizelgesinde yaşar — YM ayındaki tutar = `from_month <= YM` olan en büyük `from_month`'lu satır, `'0000-01'` sentinel'i = "baştan" (`REC_AMOUNT_BEGIN`, çözücüler `recAmountOn`/`recurringAmountIndex` engine'de). Tutar değişimi kayıt bölmez: `POST /api/recurring/:id/amount` tek atomik upsert (aynı aya ikinci yazım = düzeltme) — geçmiş projeksiyon eski tutarla korunur. recurring CRUD'u bu yüzden jenerik `crud(...)` değil elle yazılmıştır (POST iki tabloya atomik yazar; PUT yalnız kimlik kolonları). Gerçekleştirme (elle + cron) hedef ayın tutarını `recurring_amounts`'tan çözer.
- **Asistan sohbeti (Faz 34)**: `ai_conversations` (başlık ilk cümleden türer) + `ai_messages` (`plan_id` doluysa o mesaj bir UYGULAMA SONUCUdur — geri al düğmesi oraya asılır) + `ai_plans` (onay bekleyen plan; `actions` JSON, `consumed_at` tek kullanımlık kilidi). Üçü de `user_id`'li ve `TENANT_TABLES`'ta DEĞİL (ai_actions ile aynı gerekçe: auth'tan sonra doğdular, sahipsiz satırları olamaz). **`/api/all`'a KOYULMADI** — `price_history` dersinin aynısı: sohbet geçmişi her sayfa açılışında indirilecek veri değil, yalnız asistan sekmesi açılınca kendi ucundan sayfalı gelir. KVKK `GET /api/export`'a eklendi (sohbet artık sunucuda olduğuna göre kullanıcının indirebildiği veridir); silme `user_id` FK cascade ile gelir.
- **Portföy grupları (Faz 11)**: `portfolios` tanım tablosu + `trades.portfolio_id` (nullable, `ON DELETE SET NULL` → grup silinince işlem "Gruplanmamış"a düşer, kaybolmaz). Gruplama **işlem düzeyinde** bilinçli bir tercihtir: aynı sembol iki portföyde ayrı pozisyon olabilsin (farklı kurum/strateji). Yalnız raporlama katmanı — net varlık/alokasyon/projeksiyon tüm işlemleri tek listede değerlemeye devam eder. Mevcut işlemi taşımak için dar bir uç var: `PUT /api/trades/:id/portfolio` (sil+ekle modeli burada bakiyeyi iki kez oynatırdı).
- **Kredinin kalan taksidi** `first_date` + `total`'dan tarihe göre hesaplanır; biten kredi projeksiyondan kendiliğinden düşer.
- Net varlık = nakit toplamı + Σ(pozisyon değeri TRY'ye çevrili) − toplam kart borcu − kalan kredi borcu (`Σ loan.amount × loanRemaining(loan, bugün)`). Hepsi TRY canonical hesaplanır; görüntü para birimi seçiliyse nihai rakam ona çevrilir.
- **Hesap hareket defteri (Faz 15)**: `account_entries` — bakiyeyi oynatan her şey aynı `db.tx` içinde bir hareket satırı yazar. **Değişmez kural: `accounts.balance` = Σ o hesabın `account_entries.amount`'ı** (açılış bakiyesi `kind='acilis'` satırıdır). Sunucuda bakiye yalnız iki yardımcıdan değişir ([index.ts](apps/server/index.ts)): `applyEntry(t, uid, accountId, amount, meta)` (bakiye + hareket) ve `revertEntries(t, uid, source_table, source_id)` (kaynağın **yazılmış** hareketlerini okuyup tersini uygular, satırları siler) — düzenleme = revert + apply. Geri alma eski tutarı yeniden hesaplamadığı için düzenle/sil yollarında kayma olmaz. `kind`: islem/portfoy/mevduat/duzeltme/acilis. **Yeni bir bakiye etkisi eklerken doğrudan `UPDATE accounts SET balance` YAZMA** — bu iki yardımcıyı kullan, yoksa defter ile bakiye ayrışır. `kind`'e Faz 16'da `virman` eklendi (iki bacaklı transfer). `accounts` bu yüzden jenerik `crud` değil elle yazılmıştır (POST açılış hareketi, PUT elle düzeltmeyi fark kadar 'duzeltme' hareketi olarak yazar). Mevcut DB'ler `initDb()` içinde bir kez geriye dönük doldurulur (transactions/trades/deposits'ten üretilir, açıklanamayan kalan açılış satırına yazılır → hiçbir bakiye değişmez; `settings.account_entries_backfilled` bayrağı ile idempotent). Engine tarafı: [accounts.ts](packages/engine/src/accounts.ts) — `accountLedger` (yürüyen bakiye, yeniden eskiye; aynı tarihte açılış önce gelir), `ledgerDrift` (defter≠bakiye farkı — gizlenmez, uyarı olarak gösterilir), `ledgerSummary`.
- **Virman + hesap türleri + mutabakat (Faz 16)**: `transfers (date, from_account_id, to_account_id, amount, note)` = kendi hesapların arası para hareketi — **tek kayıt, iki `account_entries` satırı** (kaynak −, hedef +, `kind='virman'`), aynı `db.tx` içinde. gelir/gider defterine girmez, net varlığı değiştirmez; `revertEntries(…,"transfers",id)` iki bacağı birden geri alır (düzenleme = revert + apply, hesap değişse bile doğru). **Başkasına gönderilen para virman değil giderdir** — `transactions`'ta kalır. `accounts.kind` (`banka|nakit|araci|fon`, varsayılan `banka`): nakit cüzdanı ve aracı kurum (Midas) da birer hesap olduğundan ATM çekimi/aracıya aktarım virmandır, para sistemden çıkmaz; tür yalnız gruplama/ikon içindir, matematik değişmez. **Mutabakat**: `POST /api/accounts/:id/reconcile` gerçek bakiyeyi alır, farkı `kind='duzeltme'` hareketi olarak **yazar** (gizlemez) ve `accounts.last_recon_date/last_recon_balance` damgasını atar; fark 0 ise hareket yazılmaz, yalnız damga güncellenir. Engine: [accounts.ts](packages/engine/src/accounts.ts) — `reconcileDiff`, `reconStatus` (hic/guncel/bayat, 30 gün), `entriesSinceRecon`, `accountKindOf`. `ledgerDrift` ile karıştırma: drift defter-**içi** tutarsızlık, mutabakat **dış dünyayla** fark.
- **Gerçekleşen işlem (`transactions`) hesaba bağlıysa bakiyeyi oynatır** (sunucu tarafında, atomik) — bir harcama girince ilgili hesabın bakiyesi düşer, silinince geri gelir. Hesap seçilmezse işlem yalnızca gelir/gider defterine girer, bakiyeye dokunmaz. Not: bu Faz 1'in "accounts.balance defterden bağımsızdır" kararının yerini aldı (Faz 4.7). **Portföy işlemleri (`trades`) bakiyeyi yalnız `account_id` verilmişse oynatır** (Faz 6; ALIŞ −, SATIŞ +, DELETE geri alır — `tradeBalanceDelta`); hesap seçilmezse portföy ve nakit ayrık kalır (eski davranış, varsayılan).
- **Kayıt düzenleme (Faz 14)**: *işlem* kayıtları düzenlenebilir — `transactions`, `oneoffs`, `card_txs`, `trades`. `oneoffs`/`card_txs` jenerik `crud` PUT'unu kullanır; yan etkili `transactions` ve `trades` için elle yazılmış `PUT /api/{transactions,trades}/:id` var: tek `db.tx` içinde **eski bakiye etkisi geri alınır, yenisi uygulanır** (hesap değişse bile doğru, çünkü iki UPDATE de kendi satırının `account_id`'sini hedefler), kayıt yoksa 404. Arayüzde [EditSheet.tsx](apps/web/src/EditSheet.tsx) "+ Ekle" formlarını `edit` prop'uyla düzenle modunda açar (ayrı düzenleme formu yok; `KalemForm`/`CardTxForm`/`TradeForm` POST yerine PUT'a gider, "Kaydet, yeni ekle" gizlenir). **Kayıt türü değişmez**: `transactions` düzenlenirken tarihi ileri almak onu `oneoffs`'a çevirmez. **Tanım kayıtları da düzenlenebilir (Faz 18)**: PUT'ların çoğu jenerik `crud()`'dan gelir, tek elle yazılan `PUT /api/deposits/:id` (bakiye yan etkisi → revert+apply). Arayüzde kural "**nerede eklendiyse orada düzenlenir**": kredi/mevduat/düzenli kalem global "+ Ekle" formlarını `EditSheet` ile `edit` modunda açar; hesap adı/kart/kategori/portföy grubu kendi sekmesinde **satır içinde** düzenlenir. Düzenli kalemde **tutar yoktur** — o Faz 9'un "Değiştir" akışıdır (zaman çizelgesi; buradan değiştirmek geçmiş projeksiyonu bozardı). `crud()` PUT/DELETE eşleşen satır yoksa **404** döner (eskiden sessizce `{ok:true}` dönüyordu — veri değişmiyordu ama arayüz "kaydedildi" diyordu).
