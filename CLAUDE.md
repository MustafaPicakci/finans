# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Kişisel finans paneli: nakit hesapları, düzenli gelir/gider, kredi taksitleri, kredi kartı ekstreleri, nakit akışı takvimi ve canlı fiyatlı çok varlıklı portföy. **Auth: Faz 5.1** (kendi scrypt+session auth'umuz — [auth.ts](apps/server/auth.ts); tüm `/api` guard arkasında). **Kayıt herkese açık + e-posta doğrulaması zorunlu** (Faz 10 onboarding): **ilk kullanıcı = owner** (otomatik doğrulanır + sahipsiz veriyi devralır + otomatik giriş); **sonraki kullanıcılar** `email_verified=false` oluşturulur, aktivasyon e-postası gider, doğrulanana dek giriş 403 döner (`POST /auth/resend-verify` ile tekrar gönderilebilir). **Çok-kiracılık: Faz 5.2** — tenant tabloları `user_id` ile scope'lu (`prices/price_history` global piyasa verisi; `settings` global fx/tefas vs kullanıcı `user_settings`). **Prod ön koşulu**: çok-kullanıcı için çalışan bir e-posta yolu (+ `APP_URL`) şart — yoksa yeni kullanıcı aktive olamaz. **Faz 28**: gönderim yolu **açıkça** seçilir — `MAIL_PROVIDER` = `smtp` (varsayılan) | `gmail` | `resend`; örtük seçim (Faz 25'teki "anahtar doluysa o yola geç") bilerek kaldırıldı, çünkü hangi yolun aktif olduğu env'e bakınca görünmezse hata yanlış yolda aranır. HTTP yolları bir tercih değil zorunluluktu: **Render ücretsiz web servisleri giden SMTP portlarını (25/465/587) engelliyor** (port 25 tüm planlarda), log'da "connection timeout" olarak görünür ve ayar hatası sanılır — parola/host değiştirmek çözmez. `verifyMailConfig()` bağlantı hatalarında bu ipucunu açıkça loglar; seçilen yolun env'i eksikse hangi değişkenin eksik olduğunu söyler. **`gmail`** (Gmail API, 443): posta Google'ın kendi MTA'sından çıkar → DKIM/SPF hizalı, **domain gerektirmeden herkese ulaşır**; yetki `gmail.send` ile sınırlı (posta kutusunu okuyamaz — uygulama parolasından dar). Refresh token'dan 1 saatlik erişim jetonu üretilip önbelleklenir; açılışta gerçekten bozdurularak doğrulanır, `invalid_grant` hatası **"OAuth ekranı Testing'de kalmış"** ipucunu basar (Google o modda jetonu 7 günde bir iptal eder ve gönderim sessizce durur). Türkçe başlıklar RFC 2047 ile kodlanır. Token üreteci: [scripts/gmail-token.mjs](apps/server/scripts/gmail-token.mjs). **`resend`**: domain doğrulanmamışsa test göndereni kullanılır — **yalnız Resend hesabının kendi adresine** ulaşır (şifre sıfırlama yeter, başkasını aktive etmeye yetmez, yani çok-kullanıcılı akışı sessizce bozar); domain gelince tek değişen `MAIL_FROM`. **Yasal sayfalar (Faz 28)**: `/gizlilik` + `/kosullar` — [apps/web/public/](apps/web/public/) altında statik, **guard dışında** (giriş yapmadan okunabilmeli; Google OAuth doğrulaması anonim çeker), temiz URL için index.ts'te açık rota (yoksa SPA catch-all'una düşerdi) + `navigateFallbackDenylist` (yoksa service worker index.html döndürürdü). Faz 19: [mail.ts](apps/server/mail.ts) multipart düz metin + HTML gönderir (yalnız-HTML spam sinyalidir), açılışta `verifyMailConfig()` ile SMTP doğrulanır, `mailFromWarning()` Resend'in `From: Finans <resend>` tuzağını ve Gmail SMTP kullanımını uyarır, transport zaman aşımlıdır (yoksa yanıtsız sunucuda gönderim sonsuza dek asılı kalır — hata bile loglanmaz), gönderim hatası `lastMailError`'a yazılıp loglanır ama kayıt akışını **bloklamaz**. UI dili Türkçe; kod içi yorumlar ve enum değerleri de Türkçe (`'ALIŞ'`, `'SATIŞ'`).

pnpm workspace monorepo'dur: `apps/server` (Hono API + PostgreSQL), `apps/web` (React/Vite SPA), `packages/engine` (saf finans matematiği, ikisinin de bağımlı olduğu). Bu yapı bilinçli bir evrimin ilk adımı — hedef roadmap için [docs/PLAN.md](docs/PLAN.md)'a bakın (ledger veri modeli, mobil PWA, dosya importu, auth).

## Komutlar

```bash
pnpm install
pnpm dev            # concurrently: API (tsx watch, :8787) + Vite (:5173, /api proxy'li)
pnpm build          # pnpm -r build — her paket kendi build'ini çalıştırır (web: vite build + tsc; server/engine: tsc --noEmit)
pnpm test           # packages/engine vitest testleri (finans matematiği)
pnpm start          # prod: tek süreç, apps/server apps/web/dist statiklerini de sunar (:8787)
```

Tek bir paketi hedeflemek için `pnpm --filter @finans/server dev`, `pnpm --filter @finans/web build`, `pnpm --filter @finans/engine test` gibi filtreler kullanılır. `pnpm build` CI kapısıdır — her paket temiz geçmeli.

Node.js 22+ gerekir. **Veri tabanı PostgreSQL** (Faz 5.0'da `node:sqlite`'tan geçildi) — bağlantı `DATABASE_URL` env değişkeninden (bkz. `apps/server/.env.example`; yerel geliştirme için Docker Postgres önerilir). `apps/web`'de linter yok; vitest iki pakette çalışır — `packages/engine` (finans matematiği) ve `apps/server` (yalnız **AI ajan katmanı**: sahte sağlayıcı + enjekte edilen bağımlılıklarla, veri tabanına dokunmadan; `test-setup.ts` yalnız db.ts'in import-anı `DATABASE_URL` kontrolünü susturur). `pnpm test` = `pnpm -r test`, ikisini birden koşar. `apps/web`'de test yok. Eski SQLite verisini taşımak için: `pnpm --filter @finans/server migrate` (bir kez; `data/finans.db` → Postgres, id'ler korunur).

Docker: `docker compose up -d --build`. Compose iki servis çalıştırır: `db` (PostgreSQL, veri `./data/pg` volume'ünde) + `finans` (uygulama, `db`'ye `DATABASE_URL` ile bağlanır, healthcheck ile bekler).

## Mimari

pnpm workspace: backend = `apps/server` (Hono + PostgreSQL), frontend = `apps/web` (React/Vite SPA), paylaşılan finans matematiği = `packages/engine` (saf TS, React'e ve Hono'ya bağımlı değil). `apps/web` bu paketi `@finans/engine` olarak import eder (TS kaynağı doğrudan derlenir, ayrı build adımı gerekmez); `apps/server` da Faz 8.2'den beri tüketir (kart ekstre tutarı sunucuda `txShares` ile hesaplanır — istemciden gelen tutara güvenilmez).

### Para birimi (çok para birimi: TRY + USD)
TRY **taban (reconciliation) para birimidir**; hesaplar/gelir-gider/kart/kredi hep TRY. Yalnızca **portföy işlemleri (`trades`)** bir `currency` (TRY/USD) taşır — kripto/ABD hisse/ETF USD girilebilir. `prices`/`price_history` de sembolün doğal birimini saklar. Pozisyonlar **native** hesaplanır (`positions()` → `Position.currency`; avg/value/K/Z hep o birimde); net varlığa toplanırken `portfolioValueTry(pos, rates)` ile TRY'ye çevrilir (`rates = { usdTry }`, kaynağı `settings.fx_usd_try`). Üstteki **₺/$ görüntü seçici** (App.tsx, localStorage `finans-ccy`) net varlık özeti + KPI'ları nihai TRY rakamından çevirir (`convert(x,"TRY",ccy,rates)`); Nakit Akışı/Kayıtlar/Portföy satırları kendi biriminde kalır (portföy satırları native, projeksiyon TRY). Biçimleyici: `fmtMoney(v, ccy, dec?)` ([theme.ts](apps/web/src/theme.ts)). Yeni para birimi eklemek: `Currency` union + `convert`/`fmtMoney` + FX kuru kaynağı.

Asıl karmaşıklık burada; React'ten/Hono'dan bağımsız, 181 vitest testiyle korunuyor (`pnpm --filter @finans/engine test`). Yeni bir hesaplama kuralı eklerken önce burada test yaz.

- [date.ts](packages/engine/src/date.ts) — `hits` (ödeme günü kısa aylarda ay sonuna kayar), `ymOf`/`normYm` (ay biçimi ayrıştırma/doğrulama).

Hesap bakiyeleri bugünden başlar; recurring/loan/oneoff/kart-ekstresi hareketleri ilgili günlere işlenir. `Day.cashFunds` = o gün elde tutulan **para piyasası fonlarının** TRY değeri (`assets`'in alt kümesi); nakit sayılan fon sembolleri `settings.cash_funds`'tan (virgülle ayrık) okunur. Takvim gün rengini **etkin nakit = `bal + cashFunds`** ile belirler; fonlar Portföy sekmesindeki "nakit say" ile opt-in işaretlenir. Pür-nakit semantiği takvim dışında (Özet en düşük gün, Nakit Liste) korunur.
- [cards.ts](packages/engine/src/cards.ts) — `cardInfos`/`txShares`/`firstCutoff`/`dueOf`: kredi kartı ekstre matematiği. Harcama kesim gününe göre doğru ekstreye düşer, taksitler ardışık ekstrelere bölünür, geçmiş vadeli ekstreler ödenmiş sayılır.
- [loans.ts](packages/engine/src/loans.ts) — `loanRemaining`/`loanActiveOn`: kredinin kalan taksidi tarihten hesaplanır (elle güncelleme yok).
- [funds.ts](packages/engine/src/funds.ts) — Faz 17 "ödeme öncesi fon boz" önerisi: `cashFundSymbols`/`cashFundHoldings` (nakit sayılan fonlardan elde tutulanlar, TRY değerine göre sıralı), `cashGap(days, withinDays)` (**saf nakit** `bal` penceresinin **en derin** noktası — etkin nakde bakılsa öneri hiç çıkmazdı, ilk eksi güne göre bozulsa iki gün sonra yine açık verirdi), `fundSellSuggestion` (hangi fondan ne kadar, en geç ne zaman; fon yetmiyorsa tutar fonla sınırlanır + `covered:false`).
- [portfolio.ts](packages/engine/src/portfolio.ts) — **Faz 21: `trades` artık salt alım-satım değil, pozisyon OLAYLARI defteri** (`TradeSide = ALIŞ|SATIŞ|TEMETTÜ|BEDELSİZ`). `qtyDelta(t)` (adet etkisi: TEMETTÜ **0**, BEDELSİZ **+**) ve `cashDelta(t)` (nakit etkisi; BEDELSİZ 0) **tek kaynaktır** — adet toplama eskiden dört yerde (`positions`/`projection`/`funds`/`recall`) `side==="ALIŞ" ? +qty : -qty` diye tekrarlanıyordu, yani yeni bir tür eklendiğinde temettü sessizce SATIŞ sayılıp pozisyonu eksiltirdi. **TEMETTÜ**: adet ve maliyet değişmez, tutar `realized`'a yazılır (maliyetten düşmek satışta K/Z'yi iki kez saydırırdı). **BEDELSİZ**: adet artar, toplam maliyet sabit → ortalama maliyet kendiliğinden düşer, `price` her zaman 0. Sunucudaki `tradeBalanceDelta` da `cashDelta`'yı çağırır (ikinci kopya, yeni tür eklendiğinde ayrışırdı). `summarizeTrades` ayrıca `dividend` verir (realized'ın içinde, ayrıca raporlanır). `qtyFromAmount`/`amountFromQty` (Faz 17 tutar↔adet: tutar = **hesaba giren/çıkan para**, yani `tradeBalanceDelta`'nın tersi — `ALIŞ (tutar−fee)/price`, `SATIŞ (tutar+fee)/price`; TradeForm'un "Tutar gir" modu bunu kullanır, kaydedilen hâlâ adettir), `groupTradesByPortfolio(trades)` → `Map<portfolio_id|null, Trade[]>` (Faz 11 portföy grupları; pozisyonlar **grup başına ayrı** hesaplanır — aynı sembol iki portföyde ayrı ortalama maliyettir, tek listede değerlenince birleşir, net varlık değişmez), `portfolioGroupValueTry`; **K/Z yüzdesi**: `Position.unrealPct` + `pnlPct(pnl, cost)` (maliyet 0/negatifse `null` — 0'a bölme tek yerde çözülür). Toplam/grup oranı **yüzde ortalaması değildir**, toplam K/Z ÷ toplam maliyettir; `tradeLedger(trades)` → `TradeEntry[]` (Faz 12 hareket geçmişi: her işlemin öncesi/sonrası adet + ort. maliyet, satışta gerçekleşen K/Z, pozisyon kapandı işareti — `positions()` ile aynı matematik, ara adımları verir) + `summarizeTrades`; `positions(trades, prices)` → ağırlıklı ortalama maliyetli portföy (her pozisyon kendi `currency`'sinde); pozisyon kapanıp yeniden açılınca maliyet sıfırlanır. `convert(amount, from, to, rates)` (TRY↔USD), `portfolioValueTry(pos, rates)` (net varlık/alokasyon için TRY toplama), `portfolioValueHistory(trades, priceHistory, rates)` (USD-doğal geçmiş fiyatları güncel FX ile TRY'ye çevirir); Faz 13 grafik aralıkları: `sliceValueHistory(points, "1H"|"1A"|"3A"|"6A"|"1Y"|"TÜM")` + `bucketValueHistory` (uzun pencerede kova başına SON nokta = kapanış, ilk/son korunur) + `historyChange` (dönem değişimi mutlak+%). **Çözünürlük gündür** — `price_history` günde bir anlık görüntü tutar, aralık düğmeleri pencereyi daraltır, veriyi sıklaştırmaz.
- **Faz 27 — grafiğin iki modu**: `portfolioValueDecomposition` (değer + `contributed` + `gain` + `covered`) ve `twrSeries`/`rebasePct`/`symbolPriceSeries`/`symbolValueHistory`/`heldSymbols`/`coveredOnly`. Değer eğrisi tek başına "portföyüm arttı" der ama artışın ne kadarının KÂR, ne kadarının yeni para olduğunu söylemez; konan net para zaten `cashDelta`'nın tersidir (TEMETTÜ katkıyı AZALTIR → kâr sayılır, BEDELSİZ değiştirmez), böylece Δdeğer = Δkatkı + Δkâr tanımı gereği tam tutar. `walkValueHistory` tek yürüyüşte değer/katkı/kapsam üretir ve `portfolioValueHistory` onun ince sarmalayıcısıdır — iki kopya olsaydı biri yeni bir olay türünde sessizce ayrışırdı. **Kapsam kuralı**: fiyatı bilinmeyen AÇIK pozisyon o güne 0 katkı verir, yani seri portföyü küçük gösterir; TEFAS geriye doldurulamadığından bu sessiz eksiklik grafikte **sahte sıçramaya** dönüşürdü — `coveredOnly` o günleri eler, arayüz kaç gün düştüğünü yazar (karar PENCERE BAŞINA verilir: fiyat geçmişi olmayan bir sembol alınca katı kural son 1 ayı tamamen boşaltıp grafiği bozuk gösteriyordu). **% modunda portföy TWR'dir** (para giriş-çıkışı arındırılmış; basit değer oranı aynı veride %142 derken TWR %21 diyor — testli), **sembol/referans ise saf FİYAT getirisi** (pozisyon değerini yüzdeye çevirmek üstüne alım yapmayı "kazanç" gibi gösterirdi). TWR'nin kısıtı da testli: akış gününde fiyat anlık görüntüsü yoksa şişer.
- [statement.ts](packages/engine/src/statement.ts) — `parseStatement`/`parseDate`/`parseAmount`: yapıştırılan banka ekstresi/tablo metnini `ParsedRow[]`'a çevirir (sezgisel: ayırıcı ve tarih/tutar sütunları satırların çoğunluğuna bakılarak seçilir; bakiye sütunu varsa işaret bakiye yönünden çıkarılır). Saf + testli; toplu içe aktarmanın beyni.

Faz 16/17'de eklenen hesap türleri / mutabakat / "nakit sayılan fon" kurulmazsa sessizce atıl kalıyordu ve arayüz bunu hiç söylemiyordu — kullanıcı özelliğin varlığını bile bilmiyordu. Özet'teki "Kurulumunu tamamla" kartı yalnız gösterir; kapatılan uyarı localStorage'da (`finans-setup-dismissed`) kalır.
- [kayitlar.ts](packages/engine/src/kayitlar.ts) — **Faz 26** birleşik kayıt listesi: `tumKayitlar(data)` dört kaynağı (`transactions`/`card_txs`/`transfers`/`trades`) tek `Kayit[]`e indirger, `kayitAra`/`kayitSuz`/`kayitlariAyaGoreGrupla` süzer. Tek işaretli `tutar` alanı YETMEZ — `tutar` mutlaktır, işaret `yon` (`giris|cikis|notr`) alanındadır: virman net sıfırdır, BEDELSİZ'de para hareketi yoktur. **Arama Türkçe'ye toleranslıdır**: `toLocaleLowerCase("tr")` tek başına yetmez çünkü büyük **I** küçülünce **ı** olur — "MIGROS" araması "Migros"u bulamazdı (testle yakalandı); ayrıca ı/ş/ğ/ü/ö/ç ASCII'ye katlanır ki kullanıcı Türkçe karakter yazmadan arayabilsin.

### Backend (`apps/server/`)
- [db.ts](apps/server/db.ts) — **PostgreSQL** (`pg` havuzu, `DATABASE_URL`). Şema `initDb()` içinde `CREATE TABLE IF NOT EXISTS` ile (server başlarken `await initDb()`). `node:sqlite` senkrondu; `pg` async olduğundan `db` yüzeyi de async: `db.all/get/run(sql, ...params)` ve atomik işler için `db.tx(async t => …)`. Eski `?` yer tutucuları db katmanında `$n`'e çevrilir; `INSERT ... RETURNING id` ile `run().id` (lastInsertRowid yerine). `datetime('now','localtime')`/`date('now','localtime')` yerine JS'te üretilen `nowLocal()`/`todayLocal()` parametreleri. `id` kolonları `GENERATED BY DEFAULT AS IDENTITY`, `REAL`→`double precision` (para hassasiyeti korunur). Yeni kolon eklerken `initDb()`'ye `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` deseniyle ekle. Taşıma script'i: [scripts/migrate-sqlite-to-pg.mjs](apps/server/scripts/migrate-sqlite-to-pg.mjs).
- [auth.ts](apps/server/auth.ts) — Faz 5.1 auth: `crypto.scrypt` ile parola hash/verify (sabit-zaman), server-side `sessions` (30 gün, revoke edilebilir). `index.ts`'te `/auth/*` rotaları guard'tan **önce** tanımlanır; `api.use("*")` guard'ı sonraki tüm `/api`'yi korur (401) ve `c.set("user", …)`. Kayıt herkese açık: **ilk kullanıcı** (`count===0`) owner olur (doğrulanmış + owner-bootstrap devri + otomatik giriş), **sonrakiler** doğrulanmamış oluşturulur + aktivasyon e-postası + `pending:true` (oturum açılmaz). E-posta token'ları (`verify`/`reset`) `email_tokens`'ta; `POST /auth/{verify,resend-verify,forgot,reset}`.
- [index.ts](apps/server/index.ts) — Hono rotaları. Auth guard'ından sonra: tüm okuma **tek** `GET /api/all` ucundan (frontend her mutasyon sonrası hepsini yeniden çeker), kullanıcıya scope'lu (`WHERE user_id=?`; `settings` = global + `user_settings` merge). Yazma tarafı çoğunlukla `crud(route, table, cols)` fabrikasıyla üretilir — **Faz 5.2'de crud tek noktadan tenant-scope'lar** (POST `user_id` enjekte, PUT/DELETE `WHERE id=? AND user_id=?`), yani yeni tablo için CRUD eklemek yine tek `crud(...)` çağrısı ama otomatik izole. Yeni bir tenant tablosu eklerken `TENANT_TABLES`'a da ekle (db.ts — scoping + owner devri onu kullanır). **İstisna: `transactions`** jenerik crud yerine elle yazılmış POST/DELETE (+ toplu içe aktarma için `POST /transactions/bulk`: tek db.tx içinde N kayıt, hesap/kategori sahipliği önden doğrulanır, en fazla 500 satır) kullanır çünkü yan etkisi var — `account_id` verilmişse INSERT hesabın bakiyesini `amount` kadar oynatır (gider −, gelir +), DELETE geri alır; ikisi de `BEGIN/COMMIT` ile atomik, PUT yok (düzenleme = sil + yeniden ekle). Fiyat ve ayar uçları da elle yazılmıştır. Prod'da `serveStatic` ile `apps/web/dist` sunulur (yol `apps/server`'a göre relatif — server her zaman pnpm filter ile kendi dizininden çalıştırılmalı). `node-cron` her 15 dk `refreshAll()` çağırır. **Faz 23**: `GET /api/health` guard'tan **önce** tanımlıdır (herkese açık; yalnız süreç+DB canlılığı, DB'ye erişilemezse **503** → monitör "ayakta ama kullanılamaz"ı da görsün) ve prod'da `KEEPALIVE_URL`/`APP_URL` varsa cron 10 dk'da bir kendi genel adresini yoklar — Render ücretsiz katmanı 15 dk atıllıkta uyutuyor, soğuk başlangıç mobil "SMS paylaş" akışını bitiriyordu. #### Arayüz kuralları (Faz 24 — bunlara uymayan ekran tutarsız görünür)

Beşi de gerçek bir kusurdan doğdu; yeni ekran yazarken **varsayılan** kabul et:

1. **Mobil satır dilbilgisi.** Liste satırları `Row` (`.ui-row`) mobilde sarmalanır ve düzen `order` ile **sabittir** — içerikten bağımsız olarak `satır 1: [row-lead] [row-title…] [row-amount] [row-end]`, `satır 2+: kalan kontroller`. `Row` görünmez bir `row-break` öğesi basar, kontrolleri alt satıra o iter. Dört sınıfın anlamı: `row-lead` baştaki sabit öğe (tarih/ikon/renk noktası), `row-title` satırın kimliği, `row-amount` tutar, `row-end` küçük satır eylemleri (✎ ✕). **İşaretsiz içerik alt satıra düşer** — yeni satırda bu sınıfları vermeyi unutma. Kurallar `!important` taşır çünkü bileşenler stillerini inline verir. `Row` kullanmayan özel satırlarda (Hareketler, Plan) aynı sınıflar + elle `row-break` konur. Masaüstünde bu kurallar yok: tutarı orada da sağa yaslamak için `row-title`'a `flex:1`, tutara `marginLeft:auto` inline verilir.
2. **Filtre ≠ eylem.** Görünümü değiştiren her kontrol `FiltreSeridi` içine girer (çukur şerit, ▽ işareti); veri değiştiren düğmeler kartın yüzeyinde kalır. Marka moru "sıradaki eylem"e ayrılmıştır — seçili filtre beyaz yüzey + mor metindir, mor dolgu değil.
3. **Uzun yardım metni `Aciklama` arkasına.** Bir kez okunan açıklamalar ⓘ ile katlanır (tercih localStorage'da). **İstisna**: form alanı ipuçları ve açık panel içi görev metni katlanmaz — onlar yazarken okunur.
4. **Silme onay ister.** Çıplak `<button style={css.del}>` YAZMA; `SilDugmesi` kullan ve `sonuc` ile o kaydın **yan etkisini** yaz (virman iki bacak, hesap tüm defter, kategori işlemleri kategorisiz bırakır…). Görülmeden verilen onay, onay değildir.
5. **Modal portal şart.** `Modal` `createPortal` ile `document.body`'ye çıkar. Sebep: `.tab-grid`'in `animation: … both` dolgusu tarayıcıda kalıcı transform sayılır ve `position:fixed` için kapsayıcı blok yaratır — portal olmadan sekme içinden açılan modal ekranın binlerce piksel aşağısında ortalanır. **Sekme içeriğine `transform`/`animation` eklerken bunu hatırla.**

Ayrıca: simgeler **SVG** olmalı (⏻/◐ gibi tipografik karakterler Android'de tofu ▯ çiziliyordu); mobildeki `input,select,button{min-height:40px}` dokunma hedefi kuralı küçük satır içi seçicileri devleştirir — bilinçli istisna için `.inline-select`.

### Veri modeli notları
- **Fiyat geçmişi tutulmaz.** `prices` her sembol için tek güncel satır (`PRIMARY KEY (symbol, asset_type)`). Takvimdeki geçmiş günlerin portföy değeri de bugünkü fiyatla değerlenir.
- **Referans endeksler (Faz 27)**: `benchmark_history (key, date, price)` — global, TL'ye çevrilmiş; kayıt [apps/server/benchmarks.ts](apps/server/benchmarks.ts) (`refreshBenchmarks`, cron'da günde bir 5 günlük pencereyle). `price_history`'ye YAZILMADI: `AssetType` kapalı bir birleşim ve TradeForm'un tür açılırını besliyor — oraya "ENDEKS" eklemek S&P 500'ü alınabilir bir varlık gibi gösterirdi. `/api/all`'da 2 yılla sınırlı gönderilir (5 seri × ~500 gün); kullanıcıya göre daraltılamaz çünkü karşılaştırmanın anlamı zaten "tutmadığın şeye göre nasılsın".
- **`price_history` global ama `/api/all` KULLANICININ sembolleriyle sınırlı gönderir** (EXISTS + trades). TEFAS tazelemesi bedavaya gelen tüm fonları (yüzlerce) her gün bu tabloya yazar — bu bilinçli (yeni fon eklenince fiyatı hazır olsun) ama filtresiz okuma her sayfa açılışında tüm piyasanın geçmişini indiriyordu (ölçüldü: 770 kB / 5,5 sn, her gün büyüyor). Veri tek yerde kullanılıyor: portföy değer grafiği. **Yeni bir global tabloyu `/api/all`'a eklerken aynı soruyu sor**: bu satırların hepsi bu kullanıcı için anlamlı mı? (`prices` bilinçli olarak filtresiz kalır — sembol başına tek satır, ve TradeForm hiç işlem yapılmamış bir sembolün fiyatını oradan doldurur.)
- **Düzenli gelir/gider (Faz 9)**: kimlik ile tutar ayrıdır. `recurring` = kalıcı kimlik (ad/gün/tür/hedef/auto + yaşam penceresi `from_month`/`to_month`, `'YYYY-MM'` dahil); tutar `recurring_amounts (recurring_id, from_month, amount)` zaman çizelgesinde yaşar — YM ayındaki tutar = `from_month <= YM` olan en büyük `from_month`'lu satır, `'0000-01'` sentinel'i = "baştan" (`REC_AMOUNT_BEGIN`, çözücüler `recAmountOn`/`recurringAmountIndex` engine'de). Tutar değişimi kayıt bölmez: `POST /api/recurring/:id/amount` tek atomik upsert (aynı aya ikinci yazım = düzeltme) — geçmiş projeksiyon eski tutarla korunur. recurring CRUD'u bu yüzden jenerik `crud(...)` değil elle yazılmıştır (POST iki tabloya atomik yazar; PUT yalnız kimlik kolonları). Gerçekleştirme (elle + cron) hedef ayın tutarını `recurring_amounts`'tan çözer.
- **Portföy grupları (Faz 11)**: `portfolios` tanım tablosu + `trades.portfolio_id` (nullable, `ON DELETE SET NULL` → grup silinince işlem "Gruplanmamış"a düşer, kaybolmaz). Gruplama **işlem düzeyinde** bilinçli bir tercihtir: aynı sembol iki portföyde ayrı pozisyon olabilsin (farklı kurum/strateji). Yalnız raporlama katmanı — net varlık/alokasyon/projeksiyon tüm işlemleri tek listede değerlemeye devam eder. Mevcut işlemi taşımak için dar bir uç var: `PUT /api/trades/:id/portfolio` (sil+ekle modeli burada bakiyeyi iki kez oynatırdı).
- **Kredinin kalan taksidi** `first_date` + `total`'dan tarihe göre hesaplanır; biten kredi projeksiyondan kendiliğinden düşer.
- Net varlık = nakit toplamı + Σ(pozisyon değeri TRY'ye çevrili) − toplam kart borcu − kalan kredi borcu (`Σ loan.amount × loanRemaining(loan, bugün)`). Hepsi TRY canonical hesaplanır; görüntü para birimi seçiliyse nihai rakam ona çevrilir.
- **Hesap hareket defteri (Faz 15)**: `account_entries` — bakiyeyi oynatan her şey aynı `db.tx` içinde bir hareket satırı yazar. **Değişmez kural: `accounts.balance` = Σ o hesabın `account_entries.amount`'ı** (açılış bakiyesi `kind='acilis'` satırıdır). Sunucuda bakiye yalnız iki yardımcıdan değişir ([index.ts](apps/server/index.ts)): `applyEntry(t, uid, accountId, amount, meta)` (bakiye + hareket) ve `revertEntries(t, uid, source_table, source_id)` (kaynağın **yazılmış** hareketlerini okuyup tersini uygular, satırları siler) — düzenleme = revert + apply. Geri alma eski tutarı yeniden hesaplamadığı için düzenle/sil yollarında kayma olmaz. `kind`: islem/portfoy/mevduat/duzeltme/acilis. **Yeni bir bakiye etkisi eklerken doğrudan `UPDATE accounts SET balance` YAZMA** — bu iki yardımcıyı kullan, yoksa defter ile bakiye ayrışır. `kind`'e Faz 16'da `virman` eklendi (iki bacaklı transfer). `accounts` bu yüzden jenerik `crud` değil elle yazılmıştır (POST açılış hareketi, PUT elle düzeltmeyi fark kadar 'duzeltme' hareketi olarak yazar). Mevcut DB'ler `initDb()` içinde bir kez geriye dönük doldurulur (transactions/trades/deposits'ten üretilir, açıklanamayan kalan açılış satırına yazılır → hiçbir bakiye değişmez; `settings.account_entries_backfilled` bayrağı ile idempotent). Engine tarafı: [accounts.ts](packages/engine/src/accounts.ts) — `accountLedger` (yürüyen bakiye, yeniden eskiye; aynı tarihte açılış önce gelir), `ledgerDrift` (defter≠bakiye farkı — gizlenmez, uyarı olarak gösterilir), `ledgerSummary`.
- **Virman + hesap türleri + mutabakat (Faz 16)**: `transfers (date, from_account_id, to_account_id, amount, note)` = kendi hesapların arası para hareketi — **tek kayıt, iki `account_entries` satırı** (kaynak −, hedef +, `kind='virman'`), aynı `db.tx` içinde. gelir/gider defterine girmez, net varlığı değiştirmez; `revertEntries(…,"transfers",id)` iki bacağı birden geri alır (düzenleme = revert + apply, hesap değişse bile doğru). **Başkasına gönderilen para virman değil giderdir** — `transactions`'ta kalır. `accounts.kind` (`banka|nakit|araci|fon`, varsayılan `banka`): nakit cüzdanı ve aracı kurum (Midas) da birer hesap olduğundan ATM çekimi/aracıya aktarım virmandır, para sistemden çıkmaz; tür yalnız gruplama/ikon içindir, matematik değişmez. **Mutabakat**: `POST /api/accounts/:id/reconcile` gerçek bakiyeyi alır, farkı `kind='duzeltme'` hareketi olarak **yazar** (gizlemez) ve `accounts.last_recon_date/last_recon_balance` damgasını atar; fark 0 ise hareket yazılmaz, yalnız damga güncellenir. Engine: [accounts.ts](packages/engine/src/accounts.ts) — `reconcileDiff`, `reconStatus` (hic/guncel/bayat, 30 gün), `entriesSinceRecon`, `accountKindOf`. `ledgerDrift` ile karıştırma: drift defter-**içi** tutarsızlık, mutabakat **dış dünyayla** fark.
- **Gerçekleşen işlem (`transactions`) hesaba bağlıysa bakiyeyi oynatır** (sunucu tarafında, atomik) — bir harcama girince ilgili hesabın bakiyesi düşer, silinince geri gelir. Hesap seçilmezse işlem yalnızca gelir/gider defterine girer, bakiyeye dokunmaz. Not: bu Faz 1'in "accounts.balance defterden bağımsızdır" kararının yerini aldı (Faz 4.7). **Portföy işlemleri (`trades`) bakiyeyi yalnız `account_id` verilmişse oynatır** (Faz 6; ALIŞ −, SATIŞ +, DELETE geri alır — `tradeBalanceDelta`); hesap seçilmezse portföy ve nakit ayrık kalır (eski davranış, varsayılan).
- **Kayıt düzenleme (Faz 14)**: *işlem* kayıtları düzenlenebilir — `transactions`, `oneoffs`, `card_txs`, `trades`. `oneoffs`/`card_txs` jenerik `crud` PUT'unu kullanır; yan etkili `transactions` ve `trades` için elle yazılmış `PUT /api/{transactions,trades}/:id` var: tek `db.tx` içinde **eski bakiye etkisi geri alınır, yenisi uygulanır** (hesap değişse bile doğru, çünkü iki UPDATE de kendi satırının `account_id`'sini hedefler), kayıt yoksa 404. Arayüzde [EditSheet.tsx](apps/web/src/EditSheet.tsx) "+ Ekle" formlarını `edit` prop'uyla düzenle modunda açar (ayrı düzenleme formu yok; `KalemForm`/`CardTxForm`/`TradeForm` POST yerine PUT'a gider, "Kaydet, yeni ekle" gizlenir). **Kayıt türü değişmez**: `transactions` düzenlenirken tarihi ileri almak onu `oneoffs`'a çevirmez. **Tanım kayıtları da düzenlenebilir (Faz 18)**: PUT'ların çoğu jenerik `crud()`'dan gelir, tek elle yazılan `PUT /api/deposits/:id` (bakiye yan etkisi → revert+apply). Arayüzde kural "**nerede eklendiyse orada düzenlenir**": kredi/mevduat/düzenli kalem global "+ Ekle" formlarını `EditSheet` ile `edit` modunda açar; hesap adı/kart/kategori/portföy grubu kendi sekmesinde **satır içinde** düzenlenir. Düzenli kalemde **tutar yoktur** — o Faz 9'un "Değiştir" akışıdır (zaman çizelgesi; buradan değiştirmek geçmiş projeksiyonu bozardı). `crud()` PUT/DELETE eşleşen satır yoksa **404** döner (eskiden sessizce `{ok:true}` dönüyordu — veri değişmiyordu ama arayüz "kaydedildi" diyordu).
