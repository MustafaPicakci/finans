# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Kişisel finans paneli: nakit hesapları, düzenli gelir/gider, kredi taksitleri, kredi kartı ekstreleri, nakit akışı takvimi ve canlı fiyatlı çok varlıklı portföy. **Auth: Faz 5.1** (kendi scrypt+session auth'umuz — [auth.ts](apps/server/auth.ts); tüm `/api` guard arkasında). **Kayıt herkese açık + e-posta doğrulaması zorunlu** (Faz 10 onboarding): **ilk kullanıcı = owner** (otomatik doğrulanır + sahipsiz veriyi devralır + otomatik giriş); **sonraki kullanıcılar** `email_verified=false` oluşturulur, aktivasyon e-postası gider, doğrulanana dek giriş 403 döner (`POST /auth/resend-verify` ile tekrar gönderilebilir). **Çok-kiracılık: Faz 5.2** — tenant tabloları `user_id` ile scope'lu (`prices/price_history` global piyasa verisi; `settings` global fx/tefas vs kullanıcı `user_settings`). **Prod ön koşulu**: çok-kullanıcı için çalışan SMTP env'i (`SMTP_*` + `APP_URL`) şart — yoksa yeni kullanıcı aktive olamaz (açılışta uyarı loglanır). UI dili Türkçe; kod içi yorumlar ve enum değerleri de Türkçe (`'ALIŞ'`, `'SATIŞ'`).

pnpm workspace monorepo'dur: `apps/server` (Hono API + PostgreSQL), `apps/web` (React/Vite SPA), `packages/engine` (saf finans matematiği, ikisinin de bağımlı olduğu). Bu yapı bilinçli bir evrimin ilk adımı — hedef roadmap için [docs/PLAN.md](docs/PLAN.md)'a bakın (ledger veri modeli, mobil PWA, dosya importu, auth).

## Komutlar

```bash
pnpm install
pnpm dev            # concurrently: API (tsx watch, :8787) + Vite (:5173, /api proxy'li)
pnpm build          # pnpm -r build — her paket kendi build'ini çalıştırır (web: vite build + tsc; server/engine: tsc --noEmit)
pnpm test           # packages/engine vitest testleri (finans matematiği)
pnpm start          # prod: tek süreç, apps/server apps/web/dist statiklerini de sunar (:8787)
```

Tek bir paketi hedeflemek için `pnpm --filter @finans/server dev`, `pnpm --filter @finans/web build`, `pnpm --filter @finans/engine test` gibi filtreler kullanılır. `pnpm build` CI kapısıdır — her paket temiz geçmeli.

Node.js 22+ gerekir. **Veri tabanı PostgreSQL** (Faz 5.0'da `node:sqlite`'tan geçildi) — bağlantı `DATABASE_URL` env değişkeninden (bkz. `apps/server/.env.example`; yerel geliştirme için Docker Postgres önerilir). `apps/web`'de linter yok; `packages/engine`'de vitest var, başka yerde test yok. Eski SQLite verisini taşımak için: `pnpm --filter @finans/server migrate` (bir kez; `data/finans.db` → Postgres, id'ler korunur).

Docker: `docker compose up -d --build`. Compose iki servis çalıştırır: `db` (PostgreSQL, veri `./data/pg` volume'ünde) + `finans` (uygulama, `db`'ye `DATABASE_URL` ile bağlanır, healthcheck ile bekler).

## Mimari

pnpm workspace: backend = `apps/server` (Hono + PostgreSQL), frontend = `apps/web` (React/Vite SPA), paylaşılan finans matematiği = `packages/engine` (saf TS, React'e ve Hono'ya bağımlı değil). `apps/web` bu paketi `@finans/engine` olarak import eder (TS kaynağı doğrudan derlenir, ayrı build adımı gerekmez); `apps/server` da Faz 8.2'den beri tüketir (kart ekstre tutarı sunucuda `txShares` ile hesaplanır — istemciden gelen tutara güvenilmez).

### Para birimi (çok para birimi: TRY + USD)
TRY **taban (reconciliation) para birimidir**; hesaplar/gelir-gider/kart/kredi hep TRY. Yalnızca **portföy işlemleri (`trades`)** bir `currency` (TRY/USD) taşır — kripto/ABD hisse/ETF USD girilebilir. `prices`/`price_history` de sembolün doğal birimini saklar. Pozisyonlar **native** hesaplanır (`positions()` → `Position.currency`; avg/value/K/Z hep o birimde); net varlığa toplanırken `portfolioValueTry(pos, rates)` ile TRY'ye çevrilir (`rates = { usdTry }`, kaynağı `settings.fx_usd_try`). Üstteki **₺/$ görüntü seçici** (App.tsx, localStorage `finans-ccy`) net varlık özeti + KPI'ları nihai TRY rakamından çevirir (`convert(x,"TRY",ccy,rates)`); Nakit Akışı/Rapor/Portföy satırları kendi biriminde kalır (portföy satırları native, projeksiyon TRY). Biçimleyici: `fmtMoney(v, ccy, dec?)` ([theme.ts](apps/web/src/theme.ts)). Yeni para birimi eklemek: `Currency` union + `convert`/`fmtMoney` + FX kuru kaynağı.

Asıl karmaşıklık burada; React'ten/Hono'dan bağımsız, 46 vitest testiyle korunuyor (`pnpm --filter @finans/engine test`). Yeni bir hesaplama kuralı eklerken önce burada test yaz.

- [date.ts](packages/engine/src/date.ts) — `hits` (ödeme günü kısa aylarda ay sonuna kayar), `ymOf`/`normYm` (ay biçimi ayrıştırma/doğrulama).

Hesap bakiyeleri bugünden başlar; recurring/loan/oneoff/kart-ekstresi hareketleri ilgili günlere işlenir. `Day.cashFunds` = o gün elde tutulan **para piyasası fonlarının** TRY değeri (`assets`'in alt kümesi); nakit sayılan fon sembolleri `settings.cash_funds`'tan (virgülle ayrık) okunur. Takvim gün rengini **etkin nakit = `bal + cashFunds`** ile belirler; fonlar Portföy sekmesindeki "nakit say" ile opt-in işaretlenir. Pür-nakit semantiği takvim dışında (Özet en düşük gün, Nakit Liste) korunur.
- [cards.ts](packages/engine/src/cards.ts) — `cardInfos`/`txShares`/`firstCutoff`/`dueOf`: kredi kartı ekstre matematiği. Harcama kesim gününe göre doğru ekstreye düşer, taksitler ardışık ekstrelere bölünür, geçmiş vadeli ekstreler ödenmiş sayılır.
- [loans.ts](packages/engine/src/loans.ts) — `loanRemaining`/`loanActiveOn`: kredinin kalan taksidi tarihten hesaplanır (elle güncelleme yok).
- [funds.ts](packages/engine/src/funds.ts) — Faz 17 "ödeme öncesi fon boz" önerisi: `cashFundSymbols`/`cashFundHoldings` (nakit sayılan fonlardan elde tutulanlar, TRY değerine göre sıralı), `cashGap(days, withinDays)` (**saf nakit** `bal` penceresinin **en derin** noktası — etkin nakde bakılsa öneri hiç çıkmazdı, ilk eksi güne göre bozulsa iki gün sonra yine açık verirdi), `fundSellSuggestion` (hangi fondan ne kadar, en geç ne zaman; fon yetmiyorsa tutar fonla sınırlanır + `covered:false`).
- [portfolio.ts](packages/engine/src/portfolio.ts) — `qtyFromAmount`/`amountFromQty` (Faz 17 tutar↔adet: tutar = **hesaba giren/çıkan para**, yani `tradeBalanceDelta`'nın tersi — `ALIŞ (tutar−fee)/price`, `SATIŞ (tutar+fee)/price`; TradeForm'un "Tutar gir" modu bunu kullanır, kaydedilen hâlâ adettir), `groupTradesByPortfolio(trades)` → `Map<portfolio_id|null, Trade[]>` (Faz 11 portföy grupları; pozisyonlar **grup başına ayrı** hesaplanır — aynı sembol iki portföyde ayrı ortalama maliyettir, tek listede değerlenince birleşir, net varlık değişmez), `portfolioGroupValueTry`; `tradeLedger(trades)` → `TradeEntry[]` (Faz 12 hareket geçmişi: her işlemin öncesi/sonrası adet + ort. maliyet, satışta gerçekleşen K/Z, pozisyon kapandı işareti — `positions()` ile aynı matematik, ara adımları verir) + `summarizeTrades`; `positions(trades, prices)` → ağırlıklı ortalama maliyetli portföy (her pozisyon kendi `currency`'sinde); pozisyon kapanıp yeniden açılınca maliyet sıfırlanır. `convert(amount, from, to, rates)` (TRY↔USD), `portfolioValueTry(pos, rates)` (net varlık/alokasyon için TRY toplama), `portfolioValueHistory(trades, priceHistory, rates)` (USD-doğal geçmiş fiyatları güncel FX ile TRY'ye çevirir); Faz 13 grafik aralıkları: `sliceValueHistory(points, "1H"|"1A"|"3A"|"6A"|"1Y"|"TÜM")` + `bucketValueHistory` (uzun pencerede kova başına SON nokta = kapanış, ilk/son korunur) + `historyChange` (dönem değişimi mutlak+%). **Çözünürlük gündür** — `price_history` günde bir anlık görüntü tutar, aralık düğmeleri pencereyi daraltır, veriyi sıklaştırmaz.
- [statement.ts](packages/engine/src/statement.ts) — `parseStatement`/`parseDate`/`parseAmount`: yapıştırılan banka ekstresi/tablo metnini `ParsedRow[]`'a çevirir (sezgisel: ayırıcı ve tarih/tutar sütunları satırların çoğunluğuna bakılarak seçilir; bakiye sütunu varsa işaret bakiye yönünden çıkarılır). Saf + testli; toplu içe aktarmanın beyni.
- [recurring.ts](packages/engine/src/recurring.ts) — `recActiveOn`: `from_month`/`to_month` aralığına göre aktiflik; `recurringAmountIndex`/`recAmountOn`/`recNextAmountChange`: tutar zaman çizelgesi çözücüleri (`REC_AMOUNT_BEGIN` = `'0000-01'` "baştan" sentinel'i).

### Backend (`apps/server/`)
- [db.ts](apps/server/db.ts) — **PostgreSQL** (`pg` havuzu, `DATABASE_URL`). Şema `initDb()` içinde `CREATE TABLE IF NOT EXISTS` ile (server başlarken `await initDb()`). `node:sqlite` senkrondu; `pg` async olduğundan `db` yüzeyi de async: `db.all/get/run(sql, ...params)` ve atomik işler için `db.tx(async t => …)`. Eski `?` yer tutucuları db katmanında `$n`'e çevrilir; `INSERT ... RETURNING id` ile `run().id` (lastInsertRowid yerine). `datetime('now','localtime')`/`date('now','localtime')` yerine JS'te üretilen `nowLocal()`/`todayLocal()` parametreleri. `id` kolonları `GENERATED BY DEFAULT AS IDENTITY`, `REAL`→`double precision` (para hassasiyeti korunur). Yeni kolon eklerken `initDb()`'ye `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` deseniyle ekle. Taşıma script'i: [scripts/migrate-sqlite-to-pg.mjs](apps/server/scripts/migrate-sqlite-to-pg.mjs).
- [auth.ts](apps/server/auth.ts) — Faz 5.1 auth: `crypto.scrypt` ile parola hash/verify (sabit-zaman), server-side `sessions` (30 gün, revoke edilebilir). `index.ts`'te `/auth/*` rotaları guard'tan **önce** tanımlanır; `api.use("*")` guard'ı sonraki tüm `/api`'yi korur (401) ve `c.set("user", …)`. Kayıt herkese açık: **ilk kullanıcı** (`count===0`) owner olur (doğrulanmış + owner-bootstrap devri + otomatik giriş), **sonrakiler** doğrulanmamış oluşturulur + aktivasyon e-postası + `pending:true` (oturum açılmaz). E-posta token'ları (`verify`/`reset`) `email_tokens`'ta; `POST /auth/{verify,resend-verify,forgot,reset}`.
- [index.ts](apps/server/index.ts) — Hono rotaları. Auth guard'ından sonra: tüm okuma **tek** `GET /api/all` ucundan (frontend her mutasyon sonrası hepsini yeniden çeker), kullanıcıya scope'lu (`WHERE user_id=?`; `settings` = global + `user_settings` merge). Yazma tarafı çoğunlukla `crud(route, table, cols)` fabrikasıyla üretilir — **Faz 5.2'de crud tek noktadan tenant-scope'lar** (POST `user_id` enjekte, PUT/DELETE `WHERE id=? AND user_id=?`), yani yeni tablo için CRUD eklemek yine tek `crud(...)` çağrısı ama otomatik izole. Yeni bir tenant tablosu eklerken `TENANT_TABLES`'a da ekle (db.ts — scoping + owner devri onu kullanır). **İstisna: `transactions`** jenerik crud yerine elle yazılmış POST/DELETE (+ toplu içe aktarma için `POST /transactions/bulk`: tek db.tx içinde N kayıt, hesap/kategori sahipliği önden doğrulanır, en fazla 500 satır) kullanır çünkü yan etkisi var — `account_id` verilmişse INSERT hesabın bakiyesini `amount` kadar oynatır (gider −, gelir +), DELETE geri alır; ikisi de `BEGIN/COMMIT` ile atomik, PUT yok (düzenleme = sil + yeniden ekle). Fiyat ve ayar uçları da elle yazılmıştır. Prod'da `serveStatic` ile `apps/web/dist` sunulur (yol `apps/server`'a göre relatif — server her zaman pnpm filter ile kendi dizininden çalıştırılmalı). `node-cron` her 15 dk `refreshAll()` çağırır. **Faz 5.4 + deploy-öncesi tur**: güvenlik başlıkları + **CSP** + prod'da **HSTS**; **genel API rate-limit** (IP 300/dk) + auth uçları (10/5dk) + e-posta başına login brute-force (5→429) + zamanlama-güvenli login; gövde sınırı 256KB (413); `app.onError` jenerik 500; yazma uçlarında güvenli JSON parse (bozuk→400); `/prices/refresh` 6/dk. KVKK: `GET /api/export` (veri indir) + `POST /api/account/delete` (parola onaylı, cascade). Yeni güvenlik davranışı eklerken bu desenleri (rate-limit helper'ı `rateLimited`, `loginFails`) izle.
- [prices.ts](apps/server/prices.ts) — Best-effort fiyat çekme. Her varlık türü (`BIST`/`FON`/`ALTIN`/`DOVIZ`/`KRIPTO`/`ETF`) için ayrı fonksiyon; bir kaynak formatını değiştirirse **sadece** ilgili fonksiyon güncellenir. `refreshAll()` yalnızca `trades` tablosunda tutulan sembolleri tazeler, `prices` tablosuna `source='auto'` ile upsert eder. **Para birimi**: fiyat sembolün *doğal* biriminde saklanır — KRIPTO/ETF işlemi USD birimliyse ham USD (`×usdTry` YAPILMAZ), TRY ise (eski) çevrilir; diğer türler TRY. USD/TRY kuru her tazelemede `settings.fx_usd_try`'ye yazılır (portföyde varlık olmasa bile, holding kontrolünden önce — görüntü çevrimi için). **Elle girilen fiyatlar KULLANICIYA ÖZEL** (Faz 5.2.1): `PUT /api/prices` global `prices`'a değil `user_prices (user_id, symbol, asset_type)` tablosuna yazar; global `prices` yalnız otomatik/piyasa fiyatı tutar. `GET /api/all` global auto + kullanıcının override'ını merge eder (override kazanır, `source='manual'`); "sıfırla" (`DELETE /api/prices/...`) kullanıcının override'ını siler → global auto'ya döner. Böylece bir kullanıcının eli başkasının değerlemesini etkilemez. `ETF` (VOO, QQQ... yurt dışı borsa) Yahoo'dan sorunsuz çekilir. **`FON` (TEFAS)**: resmi API bot-koruması arkasında olduğundan RapidAPI'deki resmi olmayan bir aracı (`RAPIDAPI_KEY` / opsiyonel `RAPIDAPI_KEY_2` env değişkenleri, `.env.example`'a bakın) kullanılır — tek fon sorgusu yok, fon türü başına (1-5) tüm liste çekilip **tamamı** saklanır (kota israf edilmesin diye sadece tutulanlar değil). NAV günde bir hesaplandığından `settings.tefas_last_fetch` ile günde bir kez çağrılır (ücretsiz kota sınırlı); birinci anahtar 429 alırsa otomatik ikinciye geçilir. Anahtar yoksa/kota dolarsa fonlar elle fiyatlanır (Portföy sekmesinde rozet+sıfırla).

### Veri modeli notları
- **Fiyat geçmişi tutulmaz.** `prices` her sembol için tek güncel satır (`PRIMARY KEY (symbol, asset_type)`). Takvimdeki geçmiş günlerin portföy değeri de bugünkü fiyatla değerlenir.
- **Düzenli gelir/gider (Faz 9)**: kimlik ile tutar ayrıdır. `recurring` = kalıcı kimlik (ad/gün/tür/hedef/auto + yaşam penceresi `from_month`/`to_month`, `'YYYY-MM'` dahil); tutar `recurring_amounts (recurring_id, from_month, amount)` zaman çizelgesinde yaşar — YM ayındaki tutar = `from_month <= YM` olan en büyük `from_month`'lu satır, `'0000-01'` sentinel'i = "baştan" (`REC_AMOUNT_BEGIN`, çözücüler `recAmountOn`/`recurringAmountIndex` engine'de). Tutar değişimi kayıt bölmez: `POST /api/recurring/:id/amount` tek atomik upsert (aynı aya ikinci yazım = düzeltme) — geçmiş projeksiyon eski tutarla korunur. recurring CRUD'u bu yüzden jenerik `crud(...)` değil elle yazılmıştır (POST iki tabloya atomik yazar; PUT yalnız kimlik kolonları). Gerçekleştirme (elle + cron) hedef ayın tutarını `recurring_amounts`'tan çözer.
- **Portföy grupları (Faz 11)**: `portfolios` tanım tablosu + `trades.portfolio_id` (nullable, `ON DELETE SET NULL` → grup silinince işlem "Gruplanmamış"a düşer, kaybolmaz). Gruplama **işlem düzeyinde** bilinçli bir tercihtir: aynı sembol iki portföyde ayrı pozisyon olabilsin (farklı kurum/strateji). Yalnız raporlama katmanı — net varlık/alokasyon/projeksiyon tüm işlemleri tek listede değerlemeye devam eder. Mevcut işlemi taşımak için dar bir uç var: `PUT /api/trades/:id/portfolio` (sil+ekle modeli burada bakiyeyi iki kez oynatırdı).
- **Kredinin kalan taksidi** `first_date` + `total`'dan tarihe göre hesaplanır; biten kredi projeksiyondan kendiliğinden düşer.
- Net varlık = nakit toplamı + Σ(pozisyon değeri TRY'ye çevrili) − toplam kart borcu − kalan kredi borcu (`Σ loan.amount × loanRemaining(loan, bugün)`). Hepsi TRY canonical hesaplanır; görüntü para birimi seçiliyse nihai rakam ona çevrilir.
- **Hesap hareket defteri (Faz 15)**: `account_entries` — bakiyeyi oynatan her şey aynı `db.tx` içinde bir hareket satırı yazar. **Değişmez kural: `accounts.balance` = Σ o hesabın `account_entries.amount`'ı** (açılış bakiyesi `kind='acilis'` satırıdır). Sunucuda bakiye yalnız iki yardımcıdan değişir ([index.ts](apps/server/index.ts)): `applyEntry(t, uid, accountId, amount, meta)` (bakiye + hareket) ve `revertEntries(t, uid, source_table, source_id)` (kaynağın **yazılmış** hareketlerini okuyup tersini uygular, satırları siler) — düzenleme = revert + apply. Geri alma eski tutarı yeniden hesaplamadığı için düzenle/sil yollarında kayma olmaz. `kind`: islem/portfoy/mevduat/duzeltme/acilis. **Yeni bir bakiye etkisi eklerken doğrudan `UPDATE accounts SET balance` YAZMA** — bu iki yardımcıyı kullan, yoksa defter ile bakiye ayrışır. `kind`'e Faz 16'da `virman` eklendi (iki bacaklı transfer). `accounts` bu yüzden jenerik `crud` değil elle yazılmıştır (POST açılış hareketi, PUT elle düzeltmeyi fark kadar 'duzeltme' hareketi olarak yazar). Mevcut DB'ler `initDb()` içinde bir kez geriye dönük doldurulur (transactions/trades/deposits'ten üretilir, açıklanamayan kalan açılış satırına yazılır → hiçbir bakiye değişmez; `settings.account_entries_backfilled` bayrağı ile idempotent). Engine tarafı: [accounts.ts](packages/engine/src/accounts.ts) — `accountLedger` (yürüyen bakiye, yeniden eskiye; aynı tarihte açılış önce gelir), `ledgerDrift` (defter≠bakiye farkı — gizlenmez, uyarı olarak gösterilir), `ledgerSummary`.
- **Virman + hesap türleri + mutabakat (Faz 16)**: `transfers (date, from_account_id, to_account_id, amount, note)` = kendi hesapların arası para hareketi — **tek kayıt, iki `account_entries` satırı** (kaynak −, hedef +, `kind='virman'`), aynı `db.tx` içinde. Rapor'a girmez, net varlığı değiştirmez; `revertEntries(…,"transfers",id)` iki bacağı birden geri alır (düzenleme = revert + apply, hesap değişse bile doğru). **Başkasına gönderilen para virman değil giderdir** — `transactions`'ta kalır. `accounts.kind` (`banka|nakit|araci|fon`, varsayılan `banka`): nakit cüzdanı ve aracı kurum (Midas) da birer hesap olduğundan ATM çekimi/aracıya aktarım virmandır, para sistemden çıkmaz; tür yalnız gruplama/ikon içindir, matematik değişmez. **Mutabakat**: `POST /api/accounts/:id/reconcile` gerçek bakiyeyi alır, farkı `kind='duzeltme'` hareketi olarak **yazar** (gizlemez) ve `accounts.last_recon_date/last_recon_balance` damgasını atar; fark 0 ise hareket yazılmaz, yalnız damga güncellenir. Engine: [accounts.ts](packages/engine/src/accounts.ts) — `reconcileDiff`, `reconStatus` (hic/guncel/bayat, 30 gün), `entriesSinceRecon`, `accountKindOf`. `ledgerDrift` ile karıştırma: drift defter-**içi** tutarsızlık, mutabakat **dış dünyayla** fark.
- **Gerçekleşen işlem (`transactions`) hesaba bağlıysa bakiyeyi oynatır** (sunucu tarafında, atomik) — bir harcama girince ilgili hesabın bakiyesi düşer, silinince geri gelir. Hesap seçilmezse işlem yalnızca Rapor'a girer, bakiyeye dokunmaz. Not: bu Faz 1'in "accounts.balance defterden bağımsızdır" kararının yerini aldı (Faz 4.7). **Portföy işlemleri (`trades`) bakiyeyi yalnız `account_id` verilmişse oynatır** (Faz 6; ALIŞ −, SATIŞ +, DELETE geri alır — `tradeBalanceDelta`); hesap seçilmezse portföy ve nakit ayrık kalır (eski davranış, varsayılan).
- **Kayıt düzenleme (Faz 14)**: *işlem* kayıtları düzenlenebilir — `transactions`, `oneoffs`, `card_txs`, `trades`. `oneoffs`/`card_txs` jenerik `crud` PUT'unu kullanır; yan etkili `transactions` ve `trades` için elle yazılmış `PUT /api/{transactions,trades}/:id` var: tek `db.tx` içinde **eski bakiye etkisi geri alınır, yenisi uygulanır** (hesap değişse bile doğru, çünkü iki UPDATE de kendi satırının `account_id`'sini hedefler), kayıt yoksa 404. Arayüzde [EditSheet.tsx](apps/web/src/EditSheet.tsx) "+ Ekle" formlarını `edit` prop'uyla düzenle modunda açar (ayrı düzenleme formu yok; `KalemForm`/`CardTxForm`/`TradeForm` POST yerine PUT'a gider, "Kaydet, yeni ekle" gizlenir). **Kayıt türü değişmez**: `transactions` düzenlenirken tarihi ileri almak onu `oneoffs`'a çevirmez. *Tanım* kayıtları (hesap/kart/kredi/kategori/mevduat/düzenli kalem) hâlâ sil + yeniden ekle (tutar için Faz 9 "Değiştir" akışı).
