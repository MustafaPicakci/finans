# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Kişisel finans paneli: nakit hesapları, düzenli gelir/gider, kredi taksitleri, kredi kartı ekstreleri, nakit akışı takvimi ve canlı fiyatlı çok varlıklı portföy. **Auth: Faz 5.1** (kendi scrypt+session auth'umuz — [auth.ts](apps/server/auth.ts); tüm `/api` guard arkasında). **Kayıt herkese açık + e-posta doğrulaması zorunlu** (Faz 10 onboarding): **ilk kullanıcı = owner** (otomatik doğrulanır + sahipsiz veriyi devralır + otomatik giriş); **sonraki kullanıcılar** `email_verified=false` oluşturulur, aktivasyon e-postası gider, doğrulanana dek giriş 403 döner (`POST /auth/resend-verify` ile tekrar gönderilebilir). **Çok-kiracılık: Faz 5.2** — tenant tabloları `user_id` ile scope'lu (`prices/price_history` global piyasa verisi; `settings` global fx/tefas vs kullanıcı `user_settings`). **Prod ön koşulu**: çok-kullanıcı için çalışan bir e-posta yolu (+ `APP_URL`) şart — yoksa yeni kullanıcı aktive olamaz. **Faz 28**: gönderim yolu **açıkça** seçilir — `MAIL_PROVIDER` = `smtp` (varsayılan) | `gmail` | `resend`; örtük seçim (Faz 25'teki "anahtar doluysa o yola geç") bilerek kaldırıldı, çünkü hangi yolun aktif olduğu env'e bakınca görünmezse hata yanlış yolda aranır. HTTP yolları bir tercih değil zorunluluktu: **Render ücretsiz web servisleri giden SMTP portlarını (25/465/587) engelliyor** (port 25 tüm planlarda), log'da "connection timeout" olarak görünür ve ayar hatası sanılır — parola/host değiştirmek çözmez. `verifyMailConfig()` bağlantı hatalarında bu ipucunu açıkça loglar; seçilen yolun env'i eksikse hangi değişkenin eksik olduğunu söyler. **`gmail`** (Gmail API, 443): posta Google'ın kendi MTA'sından çıkar → DKIM/SPF hizalı, **domain gerektirmeden herkese ulaşır**; yetki `gmail.send` ile sınırlı (posta kutusunu okuyamaz — uygulama parolasından dar). Refresh token'dan 1 saatlik erişim jetonu üretilip önbelleklenir; açılışta gerçekten bozdurularak doğrulanır, `invalid_grant` hatası **"OAuth ekranı Testing'de kalmış"** ipucunu basar (Google o modda jetonu 7 günde bir iptal eder ve gönderim sessizce durur). Türkçe başlıklar RFC 2047 ile kodlanır. Token üreteci: [scripts/gmail-token.mjs](apps/server/scripts/gmail-token.mjs). **`resend`**: domain doğrulanmamışsa test göndereni kullanılır — **yalnız Resend hesabının kendi adresine** ulaşır (şifre sıfırlama yeter, başkasını aktive etmeye yetmez, yani çok-kullanıcılı akışı sessizce bozar); domain gelince tek değişen `MAIL_FROM`. **Yasal sayfalar (Faz 28)**: `/gizlilik` + `/kosullar` — [apps/web/public/](apps/web/public/) altında statik, **guard dışında** (giriş yapmadan okunabilmeli; Google OAuth doğrulaması anonim çeker), temiz URL için index.ts'te açık rota (yoksa SPA catch-all'una düşerdi) + `navigateFallbackDenylist` (yoksa service worker index.html döndürürdü). Faz 19: [mail.ts](apps/server/mail.ts) multipart düz metin + HTML gönderir (yalnız-HTML spam sinyalidir), açılışta `verifyMailConfig()` ile SMTP doğrulanır, `mailFromWarning()` Resend'in `From: Finans <resend>` tuzağını ve Gmail SMTP kullanımını uyarır, transport zaman aşımlıdır (yoksa yanıtsız sunucuda gönderim sonsuza dek asılı kalır — hata bile loglanmaz), gönderim hatası `lastMailError`'a yazılıp loglanır ama kayıt akışını **bloklamaz**. **Veri uçtan uca şifreli (E2EE, `e2ee` branch'i, aşama 0–6)**: kullanıcının tutarları, adları ve asistan sohbetleri sunucuda AES-GCM zarflarındadır, anahtar yalnız tarayıcıdadır — ayrıntı aşağıda "Sıfır bilgi şifreleme" ve [docs/E2EE.md](docs/E2EE.md). UI dili Türkçe; kod içi yorumlar ve enum değerleri de Türkçe (`'ALIŞ'`, `'SATIŞ'`).

pnpm workspace monorepo'dur: `apps/server` (Hono API + PostgreSQL), `apps/web` (React/Vite SPA), `packages/engine` (saf finans matematiği, ikisinin de bağımlı olduğu). Bu yapı bilinçli bir evrimin ilk adımı — hedef roadmap için [docs/PLAN.md](docs/PLAN.md)'a bakın (ledger veri modeli, mobil PWA, dosya importu, auth).

## Komutlar

```bash
pnpm install
pnpm dev            # concurrently: API (tsx watch, :8787) + Vite (:5173, /api proxy'li)
pnpm build          # pnpm -r build — her paket kendi build'ini çalıştırır (web: vite build + tsc; server/engine: tsc --noEmit)
pnpm test           # packages/engine vitest testleri (finans matematiği)
pnpm start          # prod: tek süreç, apps/server apps/web/dist statiklerini de sunar (:8787)
```

Tek bir paketi hedeflemek için `pnpm --filter @finans/server dev`, `pnpm --filter @finans/web build`, `pnpm --filter @finans/engine test` gibi filtreler kullanılır. `pnpm build` CI kapısıdır — her paket temiz geçmeli.

Node.js 22+ gerekir. **Veri tabanı PostgreSQL** (Faz 5.0'da `node:sqlite`'tan geçildi) — bağlantı `DATABASE_URL` env değişkeninden (bkz. `apps/server/.env.example`; yerel geliştirme için Docker Postgres önerilir). `apps/web`'de linter yok; vitest iki pakette çalışır — `packages/engine` (finans matematiği) ve `apps/server` (yalnız **AI ajan katmanı**: sahte sağlayıcı + enjekte edilen bağımlılıklarla, veri tabanına dokunmadan; `test-setup.ts` yalnız db.ts'in import-anı `DATABASE_URL` kontrolünü susturur). `pnpm test` = `pnpm -r test`, ikisini birden koşar. `apps/web`'de test yok. Eski SQLite verisini taşımak için: `pnpm --filter @finans/server migrate` (bir kez; `data/finans.db` → Postgres, id'ler korunur). Prod verisini kopyalamak için: `pnpm prod-kopya` (yerel Docker'a yeni veritabanı ya da uzak adrese — Supabase taşıması; prod'un şemasına uyan commit'in `db.ts`'ini kendisi seçer, çünkü şimdiki `initDb()` E2EE şemasını kurar ve düz prod'un tutar/ad kolonlarını atlardı. Altındaki `prod-to-local.mjs`'i doğrudan çalıştırma: `.env` hedefi şifreli yerel `finans`'tır).

Docker: `docker compose up -d --build`. Compose iki servis çalıştırır: `db` (PostgreSQL, veri `./data/pg` volume'ünde) + `finans` (uygulama, `db`'ye `DATABASE_URL` ile bağlanır, healthcheck ile bekler).

## Mimari

pnpm workspace: backend = `apps/server` (Hono + PostgreSQL), frontend = `apps/web` (React/Vite SPA), paylaşılan finans matematiği = `packages/engine` (saf TS, React'e ve Hono'ya bağımlı değil). `apps/web` bu paketi `@finans/engine` olarak import eder (TS kaynağı doğrudan derlenir, ayrı build adımı gerekmez); `apps/server` artık yalnız tipleri ve `REC_AMOUNT_BEGIN`'i alır: E2EE'den beri **sunucu tutar hesaplamaz** (göremez) — Faz 8.2'nin "istemciden gelen tutara güvenilmez" gerekçesi sıfır bilgi modelinde düştü, çünkü istemci kullanıcının kendisidir; türetilen tutarlar (ekstre, portföy nakit etkisi, mevduat, gerçekleştirme, mutabakat farkı) tarayıcıda [yazim/tutar.ts](apps/web/src/yazim/tutar.ts)'te aynı engine fonksiyonlarıyla hesaplanır.

### Para birimi (çok para birimi: TRY + USD)
TRY **taban (reconciliation) para birimidir**; hesaplar/gelir-gider/kart/kredi hep TRY. Yalnızca **portföy işlemleri (`trades`)** bir `currency` (TRY/USD) taşır — kripto/ABD hisse/ETF USD girilebilir. `prices`/`price_history` de sembolün doğal birimini saklar. Pozisyonlar **native** hesaplanır (`positions()` → `Position.currency`; avg/value/K/Z hep o birimde); net varlığa toplanırken `portfolioValueTry(pos, rates)` ile TRY'ye çevrilir (`rates = { usdTry }`, kaynağı `settings.fx_usd_try`). Üstteki **₺/$ görüntü seçici** (App.tsx, localStorage `finans-ccy`) net varlık özeti + KPI'ları nihai TRY rakamından çevirir (`convert(x,"TRY",ccy,rates)`); Nakit Akışı/Kayıtlar/Portföy satırları kendi biriminde kalır (portföy satırları native, projeksiyon TRY). Biçimleyici: `fmtMoney(v, ccy, dec?)` ([theme.ts](apps/web/src/theme.ts)). Yeni para birimi eklemek: `Currency` union + `convert`/`fmtMoney` + FX kuru kaynağı. **Yüzdeler için `fmtPct(x, dec?, zatenYuzde?)`** (aynı dosya): işaret **`%`'in ÖNÜNE** yazılır. Çağrı yerleri bunu elle kuruyordu (`{v>0?"+":""}%{(x*100).toFixed(1)}`) ve negatifte `toFixed` kendi eksisini getirip **"%-12,5"** çıkıyordu — Türkçede yanlış, üstelik pozitifte "+%6,8" yazıp negatifte biçim değiştirmek iki rakamı kıyaslanamaz kılıyordu. Yeni yüzde gösteren her yer bu fonksiyonu çağırsın.

### Sıfır bilgi şifreleme (E2EE — aşama 0–6)
Operatör veritabanında kullanıcının tutarlarını, adlarını ve sohbetlerini **okuyamaz**; tarihler, FK'ler, türler ve semboller düz kalır (kullanıcı kararı — fiyat cron'u sembolden çalışır). Tehdit modeli, gerekçeler ve ölçümler: [docs/E2EE.md](docs/E2EE.md). Doğru cümle *"veritabanında duran kayıtlarını okuyamam"*dır, *"hiçbir şekilde erişemem"* DEĞİL (JS'i sunucu sunuyor; aktif kötü niyetli sunucu bilinçli olarak kapsam dışı).
- **Satır zarfı**: her tablonun hassas alanları tek `enc` kolonunda: `v1:<iv>:<ct>` (AES-256-GCM, DEK ile, **AAD = `<tablo>:<user_id>`**, JSON 32 baytlık kovalara boşlukla doldurulur). Aşama 5'in sunucu göçünden kalan düz biçim `p1:{json}` okunur, **yazılmaz**; göçü biten kullanıcıdan gelen `p1:{` gövdesi sunucuda reddedilir. Hangi alanın zarfa girdiği [packages/crypto/src/map.ts](packages/crypto/src/map.ts)'tedir (`ZARF`; düz kalan her kolonun gerekçesi `DUZ`'de). 18 zarflı tablo.
- **Yazma = tek boru hattı** [yazim/](apps/web/src/yazim/index.ts) `yaz()`: tutar tamamla ([tutar.ts](apps/web/src/yazim/tutar.ts)) → zarfla ([zarf.ts](apps/web/src/yazim/zarf.ts); yan etkili rotalar için işleyiciler — senkron, `Muhur` yer tutucusu bırakır) → mühürle/şifrele → gönder. `api.ts`'teki bütün yazmalar ve asistan buradan geçer; anahtar yoksa düz metne düşmez, 401. **Okuma**: `veriAc` (`/api/all`, dışa aktarma) ve `zarfAc` (asistan uçları, tablo adıyla — AAD).
- **Yeni hassas alan/tablo eklerken**: `map.ts`'e ekle (ya da düz kalacaksa `DUZ`'e gerekçesiyle), gövdesi tabloyla birebir değilse `zarf.ts`'e işleyici, sızıntı testine ([zarf.test.ts](apps/web/src/yazim/zarf.test.ts) `ROTALAR`) bir rota. Sunucu zarflı alanla SQL'de **süzemez, sıralayamaz, toplayamaz** — öyle bir ihtiyaç tarayıcıda çözülür (bkz. `SIRA`). Sunucuda `db.ts` DDL'i hâlâ eski kolonları yaratır ve `zarfGoc()` açılışta onları zarfa taşıyıp düşürür (sıfırdan kurulum ile göç aynı yoldan geçsin diye) — kolonu `ADD COLUMN` ile GERİ ekleme, kapı durdurur.
- **Kapılar** (build'de): `check-zarf-sema.ts` (DDL ↔ harita, iki yönlü), `check-no-crypto.ts` (sunucu yalnız `@finans/crypto/map`'i import eder — kriptoya link'lenmez), web'de `check-yazim.mjs` (`yazim/` dışında gövdeli `fetch` yok; gerekçeli izin listesi: auth, röle, fiyatlar, hesap silme), `check-ai-routes.ts` (yeni uç asistan kararı ister).
- **Anahtarlar** ([packages/crypto/src/keys.ts](packages/crypto/src/keys.ts), yalnız WebCrypto, **kripto npm paketi yok**): parola → PBKDF2-SHA256 600k → HKDF → `KEK` (cihazda) + `auth_token` (sunucuya; scrypt'lenir). **Parola tarayıcıdan çıkmaz.** Rastgele DEK iki kez sarılı saklanır: `dek_wrapped_pw` (KEK) ve `dek_wrapped_rk` (160 bit kurtarma kodu). DEK tarayıcıda dışa aktarılamaz CryptoKey olarak IndexedDB'de ([yazim/anahtar.ts](apps/web/src/yazim/anahtar.ts)); **oturum var ama anahtar yoksa uygulama açılmaz**, parola yeniden sorulur; çıkışta silinir.
- **Kurtarma kodu zorunlu ve uygulamadan önce**: paketi olmayan hesapta (yeni kayıt + her mevcut hesabın ilk girişi) [Kurtarma.tsx](apps/web/src/features/auth/Kurtarma.tsx) kodu gösterir, kullanıcı son 4 karakteri yazar; sıra **önce paket sunucuya, sonra anahtar cihaza**. Paket yalnız YOKSA yazılabilir (`/e2ee/kurtarma` 409).
- **Tarayıcı göçü** ([yazim/goc.ts](apps/web/src/yazim/goc.ts)): girişten sonra `p1` satırları şifrelenir, **göndermeden önce geri çözülüp karşılaştırılır**, sunucu yalnız hâlâ `p1` olan satırın üzerine yazar; bitti kararını sunucu sayarak verir (`/e2ee/tamam` → `users.e2ee_migrated_at`). Yazma kilidi yok (düz yazan istemci kalmadı), yedek önerilir ama zorunlu değil — gerekçeler docs/E2EE.md §8.
- **Şifremi unuttum**: veri şifreliyse sıfırlama ya **kurtarma koduyla** (aynı DEK yeni parolayla yeniden sarılır, veri kalır) ya da açık onayla **veriyi silerek** (kullanıcının tüm satırları şema kataloğundan bulunur); yolsuz istek 409, karar token tüketilmeden verilir. **Parola değişimi** (Hesabım) veriyi yeniden şifrelemez; sarılı paket oturuma değil eski parolanın kanıtına verilir, diğer oturumlar kapanır. Yeni parola kuralı (12+ karakter, yaygın kalıp yok) YALNIZ istemcide uygulanabilir; kurala uymayan eski parola girişi engellemez, uygulama değiştirmeyi önerir.
- **Önbellek YOK** (ölçüldü: 8.000 şifreli satırda çözme masaüstünde ~50 ms, CPU×4'te ~215 ms; prod hesabı ~200 satır). Yeniden bakma ölçütü ve hazır tasarım docs/E2EE.md §3'te.
- **Otomatik gerçekleştirme tarayıcıda** (sunucu cron'u tutar göremez): [otomatik.ts](packages/engine/src/otomatik.ts) karar verir, App açılışta sürer; karta düşen kalem yazıldıysa ekstreler **taze veriden** hesaplanır (yoksa ekstre eksik ödenir ve "ödendi" işareti eksiği kalıcılaştırır). **Geriye dönük sınır sabit gün penceresi DEĞİL, talimatın başladığı gündür** (`cards.pay_since`, `recurring.auto_since`; sunucu `talimatDamgasi` ile pasif→aktif geçişte damgalar): talimattan sonraki ödenmemiş her vade, uygulama aylar sonra açılsa bile yazılır. Eski 10/45 günlük pencere geri getirilmemeli — uygulama o süre açılmazsa ekstre hiç yazılmıyor, geçmiş vadeli ekstre borçtan düştüğü için bakiye sessizce şişik kalıyordu. Damga yoksa hiçbir şey yazılmaz.

### `packages/engine` — saf finans matematiği + tipler
Asıl karmaşıklık burada; React'ten/Hono'dan bağımsız, 181 vitest testiyle korunuyor (`pnpm --filter @finans/engine test`). Yeni bir hesaplama kuralı eklerken önce burada test yaz.
- [types.ts](packages/engine/src/types.ts) — domain tipleri (`AllData`, `Recurring`, `Trade`, ...); `apps/web/src/api.ts` bunları re-export eder.
- [date.ts](packages/engine/src/date.ts) — `hits` (ödeme günü kısa aylarda ay sonuna kayar), `ymOf`/`normYm` (ay biçimi ayrıştırma/doğrulama).
- [projection.ts](packages/engine/src/projection.ts) — `project(data, months)` → günlük `Day[]` nakit projeksiyonu. Hesap bakiyeleri bugünden başlar; recurring/loan/oneoff/kart-ekstresi hareketleri ilgili günlere işlenir. `Day.cashFunds` = o gün elde tutulan **para piyasası fonlarının** TRY değeri (`assets`'in alt kümesi); nakit sayılan fon sembolleri `settings.cash_funds`'tan (virgülle ayrık) okunur. Takvim gün rengini **etkin nakit = `bal + cashFunds`** ile belirler; fonlar Portföy sekmesindeki "nakit say" ile opt-in işaretlenir. Pür-nakit semantiği takvim dışında (Özet en düşük gün, Nakit Liste) korunur. **Faz 33 — borç ve net varlık**: `Day.total` (nakit+portföy+vadeli, borç DÜŞÜLMEMİŞ), `Day.debt` (o gün hâlâ duran ödenmemiş ekstre + kredilerin kalan taksit tutarı) ve `Day.worth` (`total − debt`). `worth` App.tsx'teki hero rakamıyla **tanım olarak aynıdır** — Özet'teki "Toplam Varlık" grafiği ile hero'nun aynı soruya iki cevap vermemesi için tanım tek yerde durur. Borç, ödeme nakitten çıktığı GÜN düşer (yoksa ödenen ekstre hem bakiyeden hem borçtan iki kez sayılırdı); testli değişmez: **ekstre/taksit ödemek net varlığı değiştirmez** (nakit azalır, borç da azalır). **Faz 35 — `netWorthBreakdown(data, rates)`**: net varlığın BİLEŞENLERİ (nakit/portföy/vadeli/kart borcu/kredi borcu). Tek sayı `Day.worth`'te vardı, kırılım ise App.tsx'in içindeki dört `useMemo`'da — yani ekran dışından (asistan) sorulamıyordu. Çapa **bugünün gerçek bakiyesidir** (hesap bakiyelerinin toplamı — E2EE aşama 1a'dan beri `totalCash(account_entries)`, kolon yok), `project(...)[0].bal` DEĞİL: gün 0 bugüne düşen PLANLI hareketleri zaten işlemiştir, oysa "ne kadar nakdim var" sorusunun cevabı bankanın şu an söylediği rakamdır — ikisi çoğu gün eşit, bugüne bir hareket düştüğünde ayrışır ve **ayrışmanın yönü testte yazılı** (kimse yanlış olanı "düzeltmesin"). Kart ve kredi borcu ayrı ayrı hesaplanır, biri diğerinden ÇIKARILARAK bulunmaz: çıkarma olsaydı projeksiyona üçüncü bir borç türü eklendiği gün o tutar sessizce "kart borcu" etiketiyle görünürdü — şimdi `kartBorcu + krediBorcu === Day.debt` testi patlar.
- [cards.ts](packages/engine/src/cards.ts) — `cardInfos`/`txShares`/`firstCutoff`/`dueOf`: kredi kartı ekstre matematiği. Harcama kesim gününe göre doğru ekstreye düşer, taksitler ardışık ekstrelere bölünür, geçmiş vadeli ekstreler ödenmiş sayılır.
- [loans.ts](packages/engine/src/loans.ts) — `loanRemaining`/`loanActiveOn`: kredinin kalan taksidi tarihten hesaplanır (elle güncelleme yok).

- [db.ts](apps/server/db.ts) — **PostgreSQL** (`pg` havuzu, `DATABASE_URL`). Şema `initDb()` içinde `CREATE TABLE IF NOT EXISTS` ile (server başlarken `await initDb()`). `node:sqlite` senkrondu; `pg` async olduğundan `db` yüzeyi de async: `db.all/get/run(sql, ...params)` ve atomik işler için `db.tx(async t => …)`. Eski `?` yer tutucuları db katmanında `$n`'e çevrilir; `INSERT ... RETURNING id` ile `run().id` (lastInsertRowid yerine). `datetime('now','localtime')`/`date('now','localtime')` yerine JS'te üretilen `nowLocal()`/`todayLocal()` parametreleri. `id` kolonları `GENERATED BY DEFAULT AS IDENTITY`, `REAL`→`double precision` (para hassasiyeti korunur). Yeni kolon eklerken `initDb()`'ye `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` deseniyle ekle. Taşıma script'i: [scripts/migrate-sqlite-to-pg.mjs](apps/server/scripts/migrate-sqlite-to-pg.mjs).
- [auth.ts](apps/server/auth.ts) — Faz 5.1 auth: `crypto.scrypt` ile parola hash/verify (sabit-zaman), server-side `sessions` (30 gün, revoke edilebilir). `index.ts`'te `/auth/*` rotaları guard'tan **önce** tanımlanır; `api.use("*")` guard'ı sonraki tüm `/api`'yi korur (401) ve `c.set("user", …)`. #### Arayüz kuralları (Faz 24 — bunlara uymayan ekran tutarsız görünür)

Beşi de gerçek bir kusurdan doğdu; yeni ekran yazarken **varsayılan** kabul et:

1. **Dokunulabilir satır (yeniden tasarım, Ekim 2026 — grup 3; kullanıcı onayı).** Kayıt listelerinde satırın TAMAMI düzenlemeyi açar (`.liste-satir` düğme), satırda ✎ ✕ YOK; silme düzenleme sayfasının içindedir (`EditSheet`/tanım sayfası `FormAlt sil`, `SilDugmesi` yan etkisiyle). Gerekçe: satır başına iki küçük hedef + yanlışlıkla ✕. Uygulanan: Kartlar (harcamalar), Hesaplar (hesap → hesap sayfası, virman, mevduat), Portföy (pozisyonlar → pozisyon sayfası, portföy grupları, işlem geçmişi), Kayıtlar, Plan (düzenli → kalem sayfası, tek seferlik, kredi). Aşağıdaki eski dilbilgisi yalnız henüz geçmemiş listelerde geçerli. Satırda yalnız gerçekten bekleyen TEK eylem kalabilir (vadesi dolan mevduatta "Hesaba geçir", ekstrede "Ödedim").
1b. **Mobil satır dilbilgisi (eski listeler).** Liste satırları `Row` (`.ui-row`) mobilde sarmalanır ve düzen `order` ile **sabittir** — içerikten bağımsız olarak `satır 1: [row-lead] [row-title…] [row-amount] [row-end]`, `satır 2+: kalan kontroller`. `Row` görünmez bir `row-break` öğesi basar, kontrolleri alt satıra o iter. Dört sınıfın anlamı: `row-lead` baştaki sabit öğe (tarih/ikon/renk noktası), `row-title` satırın kimliği, `row-amount` tutar, `row-end` küçük satır eylemleri (✎ ✕). **İşaretsiz içerik alt satıra düşer** — yeni satırda bu sınıfları vermeyi unutma. Kurallar `!important` taşır çünkü bileşenler stillerini inline verir. `Row` kullanmayan özel satırlarda (Hareketler, Plan) aynı sınıflar + elle `row-break` konur. Masaüstünde bu kurallar yok: tutarı orada da sağa yaslamak için `row-title`'a `flex:1`, tutara `marginLeft:auto` inline verilir.

Bu ayrım isim çakışması yüzünden yapıldı: `hesaplar` sekmesinde "hesap" = banka/nakit/aracı kurum, orada duran "Hesabı sil" düğmesi bir banka hesabını siliyormuş gibi okunuyordu.
  - **Ortak kural (tüm sekmeler):** Sekmelerde işlem girişi formu **ve işlem ekleme düğmesi** yoktur (yalnızca hesap/kategori/kart gibi *tanım* formları); işlem girişi global "+ Ekle"dendir — Faz 24'te bu kuralın iki istisnası (Portföy "+ İşlem", Kart "+ Harcama") kaldırıldı.
- [api.ts](apps/web/src/api.ts) — HTTP istemcisi; domain tipleri `@finans/engine`'den re-export eder.

### Veri modeli notları
- **Fiyat geçmişi tutulmaz.** `prices` her sembol için tek güncel satır (`PRIMARY KEY (symbol, asset_type)`). Takvimdeki geçmiş günlerin portföy değeri de bugünkü fiyatla değerlenir.
- **`statement_payments.tx_id` (Faz 40'ta `/api/all`'a açıldı)**: ekstre ödemesinin deftere yazdığı `transactions` satırı. Sunucu bunu Faz 8.2'den beri tutuyordu ama istemciye göndermiyordu; harcama özetinin tüketim temeli ekstre ödemesini **adından tanıyamaz** ("Akbank ekstresi" elle de yazılabilir) ve elemek zorundadır, yani alan olmadan arayüz doğru toplamı hesaplayamıyordu. Tip opsiyonel: eski sunucu/PWA önbelleği taşımaz → eleme yapılamaz ve panel bunu yazar, sessizce yanlış toplam vermez.
- **Kart harcamasının kategorisi (Faz 39)**: `card_txs.category_id` (nullable, `ON DELETE SET NULL` — `transactions.category_id` ile aynı kural: kategori silinmesi harcamayı silmez, kategorisiz bırakır). Mevcut satırlar NULL kalır ve **geriye dönük tahmin YAPILMAZ** (addan kategori türetmek, ekstre ödemesini adından tanıma hatasının aynısı olurdu). Uç tarafı tek satır: jenerik `crud("cardtxs", …)` kolon listesine eklendi — `crud` kategori SAHİPLİĞİNİ doğrulamaz (tıpkı `POST /transactions` gibi; toplu içe aktarma doğrular) ama yabancı id bir şey sızdırmaz: kullanıcının kendi kategori listesinde çözülmez, engine onu kategorisiz sayar. **Düzenli gider karta düşerken kalemin kategorisi taşınır** (`realizeOccurrence`) — öncesinde aynı kalem hesaba düşünce kategoriyi koruyor, karta düşünce sessizce kaybediyordu.
- **Kurumsal olaylar (Faz 36)**: `corporate_actions (symbol, asset_type, date, kind, value, currency)` — GLOBAL, tıpkı `price_history` gibi (bir şirketin bedelsizi herkes için aynıdır). `kind`: `'bolunme'` (value = adet çarpanı) | `'temettu'` (value = hisse başına brüt tutar). Kaynak: zaten çağırdığımız Yahoo `chart` ucu + `events=div,split` ([prices.ts](apps/server/prices.ts) `yahooEvents`/`refreshCorporateActions`) — yeni veri sözleşmesi yok. Oran `splitRatio` METNİNDEN değil ham `numerator`/`denominator`'dan okunur (Türkiye'de bedelsiz yuvarlak değildir). `/api/all`'a **`gecmis` kapısının arkasından ve kullanıcının sembolleriyle sınırlı** girer (`price_history` dersi + Faz 35'in kapısı): onu tek kullanan arayüzdeki "kaçırılan olay" kartı, asistanın okuma araçları için çekilmesi gereksiz. Tarama **günlük cron'da VE açılışta** koşar — yalnız cron'a bağlı kalsaydı deploy sonrası tablo bir güne kadar boş kalır ve uyarı hiç çıkmazdı (`autoBackfill`'in gerekçesinin aynısı). **Kapsam: yalnız BIST/ETF** (fonlar bölünmez, TEFAS NAV'a yansıtır). Yahoo BIST için **bilanço tarihi vermiyor** (`events=earn` boş döner) — şirket takvimi istenirse KAP gerekir.
- **DRIP (temettü geri yatırımı)**: `user_settings.drip_symbols` — virgülle ayrık `TYPE:SYM`, `cash_funds` deseninin aynısı (ayrı tablo açmaya değmeyecek kadar küçük bir opt-in). `cash_funds` düz sembol tutar, burada TÜR de var çünkü aynı sembol iki varlık türünde olabilir. İşaret İŞLEME değil **POZİSYONA** aittir — aynı hisseyi ikinci kez alınca hangi işlemin kazanacağı sorusu doğardı; bu yüzden anahtar hem alış formunda (karar orada verilir) hem pozisyon ayrıntısında aynı ayarı yazar ve **anında** kaydedilir (bir tercih, bir işlem değil).
- **Fiyat yaşı ve `AllData.now`**: `prices.updated_at`, fiyatın oluştuğu an DEĞİL bizim onu son kez başarıyla ÇEKTİĞİMİZ andır (Yahoo piyasa kapalıyken de son kapanışı döner, yani pazar günü çekilen bir BIST fiyatı "2 dk önce" görünür ama cuma kapanışıdır) — rozet bu yüzden "çekildi" der ve tooltip gecikmeyi (BIST ~15 dk, TEFAS günde bir NAV) açıkça yazar. Yaş `fiyatYasi(updated, now)` ([theme.ts](apps/web/src/theme.ts)) ile ölçülür ve **`now` `/api/all`'dan gelir, `Date.now()`'dan değil**: `nowLocal()` timezone taşımayan bir duvar saati damgasıdır, sunucu (Render) UTC'de kullanıcı UTC+3'te olduğundan tarayıcı saatiyle karşılaştırmak taze fiyatı sürekli "3 sa önce" gösterirdi; aynı saatten iki damganın FARKI zonedan bağımsızdır. `now` yoksa (eski sunucu/PWA önbelleği) yaş **gösterilmez**, tarayıcı saatinden uydurulmaz. Üst çubuktaki global rozet **en YENİ** otomatik damgayı alır (en eskisini değil): sorduğu soru "her fiyat taze mi" değil "tazeleme çalışıyor mu" — çekilemeyen tek bir sembol (fon kotası) en eski damgayı günlerce eski tutar ve sürekli yanlış alarm verirdi. Elle girilen fiyatlar global rozetin dışındadır (yaşları kullanıcının yazma anıdır, boru hattı hakkında bir şey söylemez) ama satır ayrıntısında "girildi" diye görünür. Mobilde yaş ⋯ menüsündeki "Fiyatları yenile"nin alt satırındadır — 390px üst çubukta yer yok, karta koymak Faz 32'de çıkarılan üçüncü kopyayı geri getirirdi.
- **Şirket takvimi (Faz 37)**: `company_events (symbol, asset_type, kind, date, tahmini)` — GLOBAL (`corporate_actions` gibi: bir şirketin bilanço günü herkes için aynıdır), sembol başına **TEK satır** (`PRIMARY KEY (symbol, asset_type, kind)`) çünkü takvimin işi olan yalnız SIRADAKİ tarih; geçmişte kalanlar her turda silinir (yoksa takvim geçmişte "yaklaşan bilanço" çizerdi). Kaynak Yahoo `quoteSummary/calendarEvents` — `chart?events=earn` BIST'te BOŞ döner (ölçüldü), bu uç ise **crumb** ister: çerez → `/v1/test/getcrumb` → `&crumb=`. Projedeki tek yeni kırılganlık bu, bilinçli kabul edildi (alternatif KAP'tı, POST sorgu ucu bot koruması arkasında ve Render'dan bağlantı hiç kurulmuyor); bozulursa yalnız bilanço satırları düşer, takvimin defter tarafı ve makro tarihler çalışır. **`tahmini` AKTARILIR, gizlenmez**: Yahoo `isEarningsDateEstimate` ile tarihin duyurulmuş mu yoksa geçen yıldan mı türetildiğini söylüyor (ölçüldü: THYAO/GARAN `false`, ASELS/BIMAS `true`) — arayüz `~` ile yazar. **İleriye dönük temettü/bedelsiz YOK** ve olmayacak: `exDividendDate` çoğu sembolde SON ex-date'i döndürüyor; yani aksiyoner olan tek olay alınamayan olay, arayüz bunu saklamak yerine "beklediğin temettüyü Plan'a tek seferlik gelir yaz" der. `/api/all`'a `gecmis` kapısının arkasından ve kullanıcının sembolleriyle sınırlı girer (`corporate_actions` deseni).
- **Referans endeksler (Faz 27)**: `benchmark_history (key, date, price)` — global, TL'ye çevrilmiş; kayıt [apps/server/benchmarks.ts](apps/server/benchmarks.ts) (`refreshBenchmarks`, cron'da günde bir 5 günlük pencereyle). `price_history`'ye YAZILMADI: `AssetType` kapalı bir birleşim ve TradeForm'un tür açılırını besliyor — oraya "ENDEKS" eklemek S&P 500'ü alınabilir bir varlık gibi gösterirdi. `/api/all`'da 2 yılla sınırlı gönderilir (5 seri × ~500 gün); kullanıcıya göre daraltılamaz çünkü karşılaştırmanın anlamı zaten "tutmadığın şeye göre nasılsın".
- **`price_history` global ama `/api/all` KULLANICININ sembolleriyle sınırlı gönderir** (EXISTS + trades). TEFAS tazelemesi bedavaya gelen tüm fonları (yüzlerce) her gün bu tabloya yazar — bu bilinçli (yeni fon eklenince fiyatı hazır olsun) ama filtresiz okuma her sayfa açılışında tüm piyasanın geçmişini indiriyordu (ölçüldü: 770 kB / 5,5 sn, her gün büyüyor). Veri tek yerde kullanılıyor: portföy değer grafiği. **Yeni bir global tabloyu `/api/all`'a eklerken aynı soruyu sor**: bu satırların hepsi bu kullanıcı için anlamlı mı? (`prices` bilinçli olarak filtresiz kalır — sembol başına tek satır, ve TradeForm hiç işlem yapılmamış bir sembolün fiyatını oradan doldurur.)
- **Düzenli gelir/gider (Faz 9)**: kimlik ile tutar ayrıdır. `recurring` = kalıcı kimlik (ad/gün/tür/hedef/auto + yaşam penceresi `from_month`/`to_month`, `'YYYY-MM'` dahil); tutar `recurring_amounts (recurring_id, from_month, amount)` zaman çizelgesinde yaşar — YM ayındaki tutar = `from_month <= YM` olan en büyük `from_month`'lu satır, `'0000-01'` sentinel'i = "baştan" (`REC_AMOUNT_BEGIN`, çözücüler `recAmountOn`/`recurringAmountIndex` engine'de). Tutar değişimi kayıt bölmez: `POST /api/recurring/:id/amount` tek atomik upsert (aynı aya ikinci yazım = düzeltme) — geçmiş projeksiyon eski tutarla korunur. recurring CRUD'u bu yüzden jenerik `crud(...)` değil elle yazılmıştır (POST iki tabloya atomik yazar; PUT yalnız kimlik kolonları). Gerçekleştirme (elle + cron) hedef ayın tutarını `recurring_amounts`'tan çözer.
- **Bildirim tabloları (Faz 44)**: `push_abonelik` (cihaz: endpoint UNIQUE — aynı tarayıcı başka hesapla açılırsa adres o hesaptan ALINIR; kullanıcı başına ≤10), `push_kuyruk` (şifreli `govde` + `zaman`/`bitis`; `bitis` geçince gönderilmez — olay günü geçtiyse "3 gün sonra" yalan olur), `push_gonderilen` (abonelik + anahtar; yeni plan gönderilmişleri eler, 90 günde budanır), `push_plan` (kural sürümü). **Hiçbiri zarflı değil ve bu bilinçli**: `govde` zaten cihaz anahtarıyla şifreli opak bayt, düz kalan endpoint/anahtar içeriği açmaya yetmez, zaman/anahtar zaten düz olan tarih ve kimliklerden ibaret. `TENANT_TABLES`'ta değiller (ai_* gerekçesi) ve `/api/all`'a girmezler; silme `user_id` cascade.
- **Asistan sohbeti (Faz 34)**: `ai_conversations` (başlık ilk cümleden türer) + `ai_messages` (`plan_id` doluysa o mesaj bir UYGULAMA SONUCUdur — geri al düğmesi oraya asılır) + `ai_plans` (onay bekleyen plan; `actions` JSON, `consumed_at` tek kullanımlık kilidi). Üçü de `user_id`'li ve `TENANT_TABLES`'ta DEĞİL (ai_actions ile aynı gerekçe: auth'tan sonra doğdular, sahipsiz satırları olamaz). **`/api/all`'a KOYULMADI** — `price_history` dersinin aynısı: sohbet geçmişi her sayfa açılışında indirilecek veri değil, yalnız asistan sekmesi açılınca kendi ucundan sayfalı gelir. KVKK `GET /api/export`'a eklendi (sohbet artık sunucuda olduğuna göre kullanıcının indirebildiği veridir); silme `user_id` FK cascade ile gelir.
- **Portföy grupları (Faz 11)**: `portfolios` tanım tablosu + `trades.portfolio_id` (nullable, `ON DELETE SET NULL` → grup silinince işlem "Gruplanmamış"a düşer, kaybolmaz). Gruplama **işlem düzeyinde** bilinçli bir tercihtir: aynı sembol iki portföyde ayrı pozisyon olabilsin (farklı kurum/strateji). Yalnız raporlama katmanı — net varlık/alokasyon/projeksiyon tüm işlemleri tek listede değerlemeye devam eder. Mevcut işlemi taşımak için dar bir uç var: `PUT /api/trades/:id/portfolio` (sil+ekle modeli burada bakiyeyi iki kez oynatırdı).
- **Kredinin kalan taksidi** `first_date` + `total`'dan tarihe göre hesaplanır; biten kredi projeksiyondan kendiliğinden düşer.
- Net varlık = nakit toplamı + Σ(pozisyon değeri TRY'ye çevrili) − toplam kart borcu − kalan kredi borcu (`Σ loan.amount × loanRemaining(loan, bugün)`). Hepsi TRY canonical hesaplanır; görüntü para birimi seçiliyse nihai rakam ona çevrilir.
- **Hesap hareket defteri (Faz 15)**: `account_entries` — bakiyeyi oynatan her şey aynı `db.tx` içinde bir hareket satırı yazar. **Değişmez kural: bakiye = Σ o hesabın `account_entries.amount`'ı** (açılış bakiyesi `kind='acilis'` satırıdır). **E2EE aşama 1a'dan beri `accounts.balance` kolonu YOKTUR**: bakiye tarayıcıda `accountBalance`/`balancesByAccount`/`totalCash` ([accounts.ts](packages/engine/src/accounts.ts)) ile türer — şifreli sayı toplanamaz, türetme de zaten bedavaydı (`/api/all` tüm hareketleri gönderiyor). Kolon, defterin bakiyeyi kuruşu kuruşuna açıkladığı doğrulanarak düşürüldü; `ledgerDrift` tanım gereği 0 olduğundan kaldırıldı. Aşağıdaki cümleler bu değişikliğe göre okunmalı: `applyEntry(t, uid, accountId, enc, meta)` artık **istemcinin kurduğu hareket zarfını** yazar (toplama yok), `revertEntries` kaynağın hareketlerini siler. Sunucuda bakiye yalnız iki yardımcıdan değişir ([index.ts](apps/server/index.ts)): `applyEntry(t, uid, accountId, amount, meta)` (bakiye + hareket) ve `revertEntries(t, uid, source_table, source_id)` (kaynağın **yazılmış** hareketlerini okuyup tersini uygular, satırları siler) — düzenleme = revert + apply. Geri alma eski tutarı yeniden hesaplamadığı için düzenle/sil yollarında kayma olmaz. `kind`: islem/portfoy/mevduat/duzeltme/acilis. **Yeni bir bakiye etkisi = yeni bir hareket**: istemci [zarf.ts](apps/web/src/yazim/zarf.ts)'te hareketin zarfını kurar (`hareket(amount, note)` — notlar sunucunun eskiden ürettiklerinin birebir aynısı), sunucu `applyEntry` ile yazar. Bakiyeyi başka bir yerde tutmaya ya da hesaplamaya çalışma. `kind`'e Faz 16'da `virman` eklendi (iki bacaklı transfer). `accounts` bu yüzden jenerik `crud` değil elle yazılmıştır (POST açılış hareketi, PUT elle düzeltmeyi fark kadar 'duzeltme' hareketi olarak yazar). Mevcut DB'ler `initDb()` içinde bir kez geriye dönük doldurulur (transactions/trades/deposits'ten üretilir, açıklanamayan kalan açılış satırına yazılır → hiçbir bakiye değişmez; `settings.account_entries_backfilled` bayrağı ile idempotent). Engine tarafı: [accounts.ts](packages/engine/src/accounts.ts) — `accountLedger` (yürüyen bakiye, yeniden eskiye; aynı tarihte açılış önce gelir), `ledgerDrift` (defter≠bakiye farkı — gizlenmez, uyarı olarak gösterilir), `ledgerSummary`.
- **Virman + hesap türleri + mutabakat (Faz 16)**: `transfers (date, from_account_id, to_account_id, amount, note)` = kendi hesapların arası para hareketi — **tek kayıt, iki `account_entries` satırı** (kaynak −, hedef +, `kind='virman'`), aynı `db.tx` içinde. gelir/gider defterine girmez, net varlığı değiştirmez; `revertEntries(…,"transfers",id)` iki bacağı birden geri alır (düzenleme = revert + apply, hesap değişse bile doğru). **Başkasına gönderilen para virman değil giderdir** — `transactions`'ta kalır. `accounts.kind` (`banka|nakit|araci|fon`, varsayılan `banka`): nakit cüzdanı ve aracı kurum (Midas) da birer hesap olduğundan ATM çekimi/aracıya aktarım virmandır, para sistemden çıkmaz; tür yalnız gruplama/ikon içindir, matematik değişmez. **Mutabakat**: `POST /api/accounts/:id/reconcile` gerçek bakiyeyi alır (E2EE: farkı tarayıcı defterden hesaplar ve hareketi zarflar), farkı `kind='duzeltme'` hareketi olarak **yazar** (gizlemez) ve `accounts.last_recon_date/last_recon_balance` damgasını atar; fark 0 ise hareket yazılmaz, yalnız damga güncellenir. Engine: [accounts.ts](packages/engine/src/accounts.ts) — `reconcileDiff`, `reconStatus` (hic/guncel/bayat, 30 gün), `entriesSinceRecon`, `accountKindOf`. (Eski `ledgerDrift` — defter-içi tutarsızlık — kolon düşünce anlamını yitirdi ve kaldırıldı; mutabakat **dış dünyayla** farktır.)
- **Gerçekleşen işlem (`transactions`) hesaba bağlıysa bakiyeyi oynatır** (E2EE: kayıt ile aynı `db.tx`'te bir hareket satırı yazılarak — bakiye kolonu yok) — bir harcama girince ilgili hesabın bakiyesi düşer, silinince geri gelir. Hesap seçilmezse işlem yalnızca gelir/gider defterine girer, bakiyeye dokunmaz. Not: bu Faz 1'in "accounts.balance defterden bağımsızdır" kararının yerini aldı (Faz 4.7). **Portföy işlemleri (`trades`) bakiyeyi yalnız `account_id` verilmişse oynatır** (Faz 6; ALIŞ −, SATIŞ +, DELETE geri alır — tutarı E2EE'den beri tarayıcı `cashDelta`'dan türetir); hesap seçilmezse portföy ve nakit ayrık kalır (eski davranış, varsayılan).
- **Kayıt düzenleme (Faz 14)**: *işlem* kayıtları düzenlenebilir — `transactions`, `oneoffs`, `card_txs`, `trades`. `oneoffs`/`card_txs` jenerik `crud` PUT'unu kullanır; yan etkili `transactions` ve `trades` için elle yazılmış `PUT /api/{transactions,trades}/:id` var: tek `db.tx` içinde **eski bakiye etkisi geri alınır, yenisi uygulanır** (hesap değişse bile doğru, çünkü iki UPDATE de kendi satırının `account_id`'sini hedefler), kayıt yoksa 404. Arayüzde [EditSheet.tsx](apps/web/src/EditSheet.tsx) "+ Ekle" formlarını `edit` prop'uyla düzenle modunda açar (ayrı düzenleme formu yok; `KalemForm`/`CardTxForm`/`TradeForm` POST yerine PUT'a gider, "Kaydet, yeni ekle" gizlenir). **Kayıt türü değişmez**: `transactions` düzenlenirken tarihi ileri almak onu `oneoffs`'a çevirmez. **Tanım kayıtları da düzenlenebilir (Faz 18)**: PUT'ların çoğu jenerik `crud()`'dan gelir, tek elle yazılan `PUT /api/deposits/:id` (bakiye yan etkisi → revert+apply). Arayüzde kural "**nerede eklendiyse orada düzenlenir**": kredi/mevduat/düzenli kalem global "+ Ekle" formlarını `EditSheet` ile `edit` modunda açar; hesap adı/kart/kategori/portföy grubu kendi sekmesinde **satır içinde** düzenlenir. Düzenli kalemde **tutar yoktur** — o Faz 9'un "Değiştir" akışıdır (zaman çizelgesi; buradan değiştirmek geçmiş projeksiyonu bozardı). `crud()` PUT/DELETE eşleşen satır yoksa **404** döner (eskiden sessizce `{ok:true}` dönüyordu — veri değişmiyordu ama arayüz "kaydedildi" diyordu).
